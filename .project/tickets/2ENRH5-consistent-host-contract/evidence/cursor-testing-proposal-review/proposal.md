# Revised proposal: shared behavior with distinct compatibility proof

Author Safeword behavior and policy once. Generate each host's packaging and mechanical adapter from the same canonical owners. Author reusable conformance scenarios once and execute their applicable examples at each required real host boundary; do not independently maintain equivalent per-host policy or scenarios.

Shared policy tests cover the policy's cases centrally. Real-boundary tests must also demonstrate that each contracted binding reaches that policy and the host honors its result, using allowed/denied controls and route-bypass checks where required. A generic plugin-loading smoke test is insufficient. Existing complete inventory and drift checks remain required.

Routine development uses targeted shared-policy, derivation and adapter tests, plus actual host proof for affected contracts before dependent work or support claims. Expensive complete compatibility runs belong at the appropriate verification/release boundary. Moving a test's cadence never removes its obligation or substitutes a cheaper test for required real-host evidence. Safeword derives applicable coverage from its registry/contracts automatically; the user does not maintain a host checklist.

Cursor IDE and CLI remain separate runtime evidence. Keep all accepted exact-version and delivery cases: native IDE 3.24.18; legacy project-hook IDE 3.8.23 and 3.24.18; CLI 2026.09.28-64d2043. Required automated IDE registration/bootstrap, catalogue, guards, lifecycle/activation/trust and continuation evidence stays mandatory wherever specified in the accepted plan. CLI, manual, other-version or other-delivery evidence cannot satisfy those obligations. CLI catalogue and allow/deny proof does not claim CLI continuation. These pins are compatibility targets, not instructions to downgrade customer installations. Current online docs explain architecture but do not certify older pinned versions.

Cloud-specific delivery/enforcement is outside this ticket. Preserve existing static project wrappers and configuration-scoped reporting with the accepted cloud-like regression; that regression cannot certify a Cloud runtime. No new per-host subagent suite is introduced. Prove the existing contracted worker/reviewer guarantees, including the accepted OpenCode V2 worker context and authority boundaries, through their real delegation path. Do not infer subagent protection from parent success.

A named agent or different model does not by itself require a duplicate full deterministic suite. Changes affecting prompts, tools, permissions, delegation or model-dependent behavior do require targeted validation of the affected promises, including reviewer routing/independence and real bounded continuation where claimed. An observed follow-up turn, not an agent's statement, proves continuation. Soft workflow guidance is not hard enforcement.

Cursor's Agents Window is an interface capable of local, cloud and remote sessions. Classify the actual execution, delivery and authority boundaries; do not infer local proof covers everything launched from that window. Any new remote/cloud support remains outside accepted scope until explicitly scoped and proved.

The native Cursor IDE diagnostic group currently has four passing cases (catalogue/helper, allow, deny, bounded continuation); CLI has three (catalogue/helper, allow, deny). These diagnostic results do not establish customer activation, complete lifecycle/admission, legacy lanes, every worker, or overall feature completion. See cursor-continuation-proof.md. The earlier reviewer assertion that native dispatch remains unproved came from stale plan status, not this newer evidence.

Acceptance for this proposal: central authoring retained; no required exact-version/delivery examples dropped; no CLI/manual/parent evidence substituted for other boundaries; no cloud scope expansion; no claim of full coverage or measured usability. The eventual NTB/TBU outcome walkthrough remains required: tests alone cannot show that users no longer need to reason about host differences. This review changes only the explanatory proposal, not accepted ticket scope or implementation plan.
