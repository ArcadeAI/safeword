# Impl Plan: Make planning gates understandable and scope-safe

**Status:** planned
**Planned on:** 2026-11-19

## Approach

Planning owners produce the existing typed outcome and authoritative facts. A shared presentation function chooses one human action from those facts and renders the problem, reason progress stopped, and action. CLI and host adapters present that same outcome through their existing native envelopes. Diagnostic details follow the primary message. Headless hosts retain the pending outcome in reviewable output and return. This child owns presentation only, including presentation of a dispute outcome supplied by its owner. [Accepted Rules](spec.md) · [Scenarios](../../../features/make-planning-gates-understandable-and-scope-safe.feature)

The riskiest assumption is that currency checking can distinguish user-visible causes without guessing from a generic stale receipt. The cheapest discriminating proof is installed CLI invalidation with reviewed artifacts, changing only execution order and then, in a separate case, the canonical approach contract. Check that the named reviews and human approval consequences differ while the authority checks still reject stale evidence. A single general “review again” message would fail.

### Persona consequences

- **Non-Technical Builder:** Gets an explanation and one action naming the relevant plan, guidance or human actor. The walkthrough must demonstrate understanding without digests or code.
- **Technical Builder:** Gets underlying diagnostics and retained evidence after the action. Only authoritative comparisons justify a named cause or changed review set.
- **Contributor role (TBU or SWM):** Can leave a reviewable headless handoff with named pending work. Its presence supports follow-up without granting new permissions.
- **Safeword Maintainer:** Keeps scope, design approval and dispute decisions with their existing owners. Rendering and a reviewer verdict cannot record a human act.

## Decisions

### Recorded Decisions

- **Decision:** Present one recovery from typed owner facts.
  **Choice:** Author one dependency-free projector over an internal v1 owner-fact model (outcome family, exact artifact or actor identity and supported cause facts). Generate a byte-identical standalone hook template from that source and import the canonical source in the CLI build. Register the hook template through the schema, reconcile it into project hooks and carry it through native bundle generation. Check source-to-template byte parity and installed adapter outcome parity for every category. Keep the public code, exit/deny semantics and machine continuation. Project the problem, stopped consequence and one action, with optional diagnostics after it. A native adapter surfaces CLI-projected text once when present and projects locally for a hook-owned deny or when CLI text is absent. Sanitize display labels and omit sensitive diagnostics from shareable output.

  Missing contract directs installed-file reconciliation. For a contract mismatch render the available digest and review ID under **Technical details** after the primary action within the existing access boundary. Unreadable context names the guidance file to repair and retry. For an absent Execution Plan, say the execution steps are missing and direct the builder to create and review the Execution Plan as one recovery. If the CLI cannot resolve, a hook that already owns a stop still projects its local facts. If the owner check itself could not run, report that check as unavailable with one action to restore the matching installation and retry. Retain the actual gate outcome and its limits. Unknown or missing facts on an existing stop use the nearest verified artifact or owner for inspection.

  Use the installed integrity owner's typed result to distinguish a missing, edited, stale or mismatched installed copy from a canonical change invalidating review on a reconciled installation. The former directs reconciliation of the installed files before review. The latter belongs to review currency.

Generated local distribution fits standalone hooks that cannot import the CLI, including project-only Cursor installs.

### Rollout

Default on with the matched supported release under YCFFNC's coordinated activation. Expand from dogfood through installed local and fresh cloud proof, including real producer and walkthrough evidence. A new hook with an older CLI renders compatible facts or uses local generic recovery. An older hook with a newer CLI retains its old presentation and may display new CLI text only where it already surfaces that output. Unknown fact versions use the existing status and one local recovery where the capable adapter can prove one. Mixed builds have no message-parity or project-wide enforcement guarantee. Preserve stored outcomes. Pause expansion if a verified stop loses its state, names the wrong owner, emits competing actions or fails the real walkthrough. Reconcile a matched known-good bundle subject to the existing unresolved-dispute rollback boundary.

YCFFNC enables new approval writes only in the matched release. An old reader skips the new event and can still misread older decisions by its historical rules. Keep approval-dependent work on the capable bundle during migration and rollback. Pause that work if a capable bundle is unavailable. Verify both directions of reader/writer skew through the approval owner before coordinated activation.

## Known deviations

A legacy receipt may be insufficient to identify what changed. Give the strongest supported statement and a single recovery action while preserving the stale verdict. Current-version discriminating cases require specific cause evidence. Mixed-version dispute protection and rollback over unresolved disputes are excluded from #4200. Dispute implementation remains with its owner.

## Doc impact

Website planning, troubleshooting and host guidance should show one-action recovery, human handoff and accurately labeled fallback, plus where to find technical details. README workflow claims should distinguish supported gated hosts from advisory surfaces and distinguish contributor or reviewer output from human authority.

## Assessment triggers

Reopen the design if an installed producer cannot distinguish a required invalidation, host output loses the pending state or repeats an action, the presenter would have to infer a scope or dispute disposition, or any walkthrough participant needs diagnostic metadata or sees competing actions.
