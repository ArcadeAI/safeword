# Spec: Let parallel sessions share test capacity safely

## Intent

Safeword should let independent worktrees participating in the current
scheduler protocol overlap small focused test runs up to an operator-chosen
shared limit, while preserving same-worktree build safety and exclusive broad
verification. The scheduler bounds participating wrapper lifetimes; it does
not cap worker processes created inside an unchanged build or Vitest command.

## Intake Brief

- **Requested by:** Alex, after the machine-global mutex repeatedly queued short focused runs behind unrelated full suites.
- **Cost of inaction:** Parallel sessions remain needlessly serialized, encouraging lock bypasses that can overload the machine or reintroduce build races.
- **Reversibility:** Two-way door. The capacity limit can default to one, restoring today's mutex behavior without changing the test command.

## Vocabulary

- **Focused run:** A test invocation naming explicit test files and eligible to consume one shared permit.
- **Broad run:** A directory, alternate configuration, coverage, done-lane, or full-suite invocation that consumes all capacity and runs exclusively.
- **Permit:** One bounded share of local test capacity among participating current-protocol wrappers.
- **Checkout mutex:** The per-worktree guard that keeps each participating package-test wrapper's complete build and test activity serialized against another participating wrapper in that checkout, even when another checkout holds a permit.

## Rave Moment

### share-test-capacity — The short check no longer waits for the suite

- **Moment:** A focused test in one worktree begins safely while another focused test runs elsewhere, yet an arriving full suite still gets its exclusive turn.
- **Beats:** A single opaque queue where a seconds-long check waits behind minutes of unrelated verification, or an unsafe lock bypass that overloads the machine.
- **They'd say:** “My sessions can test in parallel now, but Safeword still keeps the heavy runs from fighting each other.”

## Outcomes

- Eligible focused runs from participating current-protocol worktrees overlap only up to their configured shared limit.
- Same-worktree build and test commands in one OS-user capacity domain never overlap.
- Broad runs become exclusive after existing focused holders drain, and newer focused arrivals cannot starve them.
- Process death releases focused and broad capacity automatically once container absence and durable state are verifiable; indeterminate durability stays fail-closed for explicit recovery.
- Capacity one preserves the current single-run behavior, and participating new-wrapper sessions cannot disagree about the active capacity.

## Decisions

- V1 initializes one persisted shared capacity to one, preserving today's mutex behavior. Raising it to two or more is an explicit current-protocol opt-in made only while the new scheduler and any authenticated recorded legacy mutex are idle; the customer confirms every intended participating worktree uses the new wrapper. A provably held legacy mutex returns `SAFEWORD_TEST_CAPACITY_BUSY`; absence of a record is not treated as proof that no untracked legacy process exists. Every participating current-protocol process then reads the same canonical value; project-local configuration and per-process environment do not redefine that shared resource.
- The public opt-in is `safeword project test-capacity set <1..8> [--confirm-current-protocol]`. For a value above one, the single bare flag is mandatory and atomically persists the exact scheduler protocol/schema version with the capacity only after the scheduler is idle; capacity one may omit it. Valued, duplicate, false, conflicting, or unknown flags and extra tokens are invalid and change nothing. The confirmation is an explicit operator assertion—not detection of untracked legacy processes—and status reports that limitation plus the command to restore capacity one before any legacy wrapper is used.
- Before committing capacity above one on POSIX, the set command and confirmation output disclose that deliberately detached descendants are not contained and direct projects to disable detachment; retaining capacity one is an additional participating-wrapper safeguard but cannot by itself contain an already escaped process. The confirmation affirms that limitation as well as current-protocol participation; status repeats it whenever POSIX capacity exceeds one and never claims capacity one repairs deliberate escape.
- The reset surface is exactly `safeword project test-capacity reset --expected-domain <domain-id> --confirm-idle`, with each option present once, a nonempty domain value, no option values for `--confirm-idle`, and no unknown flags or extra positionals. The domain ID comes from status; reset acquires the state guard before establishing an exact current schema/domain match and positive idle proof with no checkout request, owner, waiter, or reclaiming weight, and the explicit confirmation flag then atomically restores capacity one with current protocol state. Admission and reset serialize on that guard: a request or owner registered first makes reset `BUSY`, while a reset committed first advances the version before later registration, so neither race can lose work. Malformed syntax, a missing or mismatched domain, or missing confirmation exits `SAFEWORD_TEST_CAPACITY_INVALID`; busy or unverifiable state uses its corresponding stable code. Every failure changes nothing.
- The supported capacity token is exactly one canonical unsigned decimal digit in `1..8`. Signs, leading zeros, surrounding whitespace inside the token, decimal/exponent notation, overflow, missing or duplicate positional values, and duplicate or conflicting confirmation flags are invalid and change no state. Capacity may change only while there are no checkout requests, owners, waiters, or reclaiming weight; otherwise the change is refused with a clear retry action. V1 deliberately has no drain mode: the operator must stop starting participating runs and retry after status reports idle, and `BUSY` may recur without bound while new work continues.
- Concurrent valid set commands serialize under the state guard. If the scheduler remains idle, each commits in guard order with the next state version; `BUSY` means the guarded view contains a checkout request, owner, waiter, or reclaiming weight, not mere contention or an earlier valid `set`.
- Broad runs acquire the entire canonical capacity atomically. Capacity one restores today's single-run behavior.
- A permit bounds one complete participating wrapper lifetime, not its descendant count. Safeword forwards the build and Vitest invocation unchanged; the operator chooses capacity for that command's existing worker policy. V1 does not claim to derive or enforce a machine-load limit.
- Automatic CPU- or memory-derived sizing is deferred until real usage provides a trustworthy model across operating systems and CI runners.
- A request is focused only when it has exactly one argument and that argument, resolved against the wrapper invocation's current directory without changing the original downstream token, is a literal path to an existing regular test file inside that checkout whose case-sensitive basename ends in `.test` or `.spec` followed by `.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, `.mts`, `.cjs`, or `.cts`. Multiple files, existing regular non-test files, near-miss/case variants, and mixed test/non-test arguments are broad; custom/alternate selection configuration is already broad. Classification walks the original component sequence at or below the canonical checkout root without following symlinks or reparse points; `..` may elide only a preceding component already proven to be a real directory. It rejects any aliasing component in that scope and confirms the resulting canonical parent/file remains beneath the root before admitting focus; every path component above the canonical checkout root is outside this check. The classifier rejects focus for option-prefixed tokens, `--`, glob or pattern metacharacters, nonexistent paths, directories, in-scope aliases, paths escaping the checkout lexically or canonically, unknown runner flags, mixed file/flag forms, coverage, done lanes, alternate configurations, and unfiltered runs. Rejected focus means conservative broad classification, not command rejection; the unchanged downstream runner still owns whether the invocation itself is valid. The classifier passes the validated exact file path unchanged to the real Vitest collaborator and maintains no second test-selection grammar. Classification chooses permit weight only; it is not a security boundary against a same-user file swap between validation and downstream execution. That bounded TOCTOU risk can only misclassify one caller's permit, while scheduler-state corruption can violate cross-session ownership, so state storage retains the stronger identity and no-follow protections.
- Registration, admission, cancellation, and crash cleanup occur atomically under the scheduler state guard. Each waiter receives a monotonic FIFO ticket and the same PID-plus-process-creation identity required of owners. A waiter rechecks the guarded queue after a bounded monotonic backoff, so permit release needs no loss-prone wakeup signal; tests inject the clock and barriers rather than sleeping. Before every head-admission decision, the process holding the state guard removes only waiters whose exact process instance the OS reports absent. The wrapper handles POSIX `SIGINT`/`SIGTERM` and Windows `CTRL_C_EVENT`/`CTRL_BREAK_EVENT` by setting an internal cancellation flag before teardown; only that flag produces `SAFEWORD_TEST_CAPACITY_CANCELLED` and exit 130, while an unflagged downstream exit 130 is forwarded unchanged. Cancellation removes only the caller's identity and ticket. Tests invoke the same handler seam deterministically rather than treating host signal delivery as the assertion. If identity cannot be verified, admission fails closed with recovery guidance instead of skipping the head.
- Consecutive focused requests at the live queue head may fill capacity; a broad request is admitted only when it reaches the head and all capacity is free, then runs alone. No later request can overtake the head.
- No waiter holds a partial allocation. Ownership acquisition and release are atomic, and recovery either uses OS-released ownership or validates process birth identity in addition to PID; elapsed age alone never authorizes reclaiming a live owner's capacity.
- V1 first use atomically creates one owner-only scheduler state guard and one version-1 current schema/protocol state at capacity one, including the first checkout's canonical-root-to-filesystem-identity mapping and the initializing wrapper's durable checkout request. That request is metadata, not scheduler admission: it pins the mapping while the wrapper releases the state guard and blocks on the derived checkout mutex, then ordinary admission converts it to scheduler ownership after the mutex is acquired. Capacity changes and reset therefore see `BUSY` throughout this window rather than mistaking it for idle. Concurrent first wrappers serialize through that single canonical guard and checkout key; interrupted creation recovers only authenticated temporary artifacts, unsafe pre-existing artifacts fail closed, and a compatible older state migrates once under the idle guard. Each commit writes and flushes a temporary file, then atomically replaces state using the platform durability contract: rename plus parent-directory flush on POSIX, and same-volume `MoveFileEx` replacement with `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH` on Windows. If that required primitive is unavailable, mutation fails before admission with `SAFEWORD_TEST_CAPACITY_PLATFORM_UNSUPPORTED`; an available primitive that fails returns `SAFEWORD_TEST_CAPACITY_STATE_UNSAFE`. A crash before replacement leaves the prior valid state; a crash after replacement exposes the complete new state; an unreadable state fails closed.
- The live state is self-authenticating and replaced atomically as one file. After an interrupted platform durability commit, restart accepts only a complete authenticated old or new state, durably recommits that state with the same platform primitive, and then admits; a partial or unauthenticated file fails closed. No second journal state machine is required because atomic replacement cannot expose partial live bytes and either complete side is safe.
- Scheduler/configuration storage uses an owner-only directory opened without following symlinks or reparse points. Guarded operations pin and revalidate the directory/file identity across validation, temporary creation, flush, and rename; reject unexpected hard-link counts; and fail closed if an inode/file ID, ownership, permissions, link count, or canonical parent changes. Handle-relative creation is a required platform primitive; if unavailable, admission fails with `SAFEWORD_TEST_CAPACITY_PLATFORM_UNSUPPORTED` rather than falling back to a path-based commit. A small first-party native runtime helper supplies `openat`/directory-handle operations, Linux `pidfd_open`/`pidfd_send_signal`, Windows file IDs and DACLs, Job Objects, `MoveFileEx`, and Darwin process info. Release packaging must provide and integrity-check that helper for every supported OS/architecture. A missing or mismatched helper may retain the legacy capacity-one path only before current-protocol state exists; after initialization every public operation fails closed with the platform code and the exact helper repair command rather than switching protocols.
- Under that guard, state holds canonical capacity, next FIFO ticket, durable checkout requests keyed by exact wrapper and checkout mapping, waiter identities, and owner identities with weight `1` for focused or the full canonical capacity for broad. A checkout request is written before releasing the state guard to acquire or wait on its derived mutex and is removed only when that mutex is relinquished or exact dead-request recovery proves safe; conversion to waiter or owner never leaves the mapping unreferenced. Admission, cancellation, owner release, and verified dead-process pruning are single guarded state transitions; a broad owner is recorded only from an empty owner set. Process evidence must reconcile every repository lifetime to exactly one durable activation and release, and every owner to one keyed wrapper; duplicate/replayed releases are idempotent, reservation-to-active failure starts no repository process and removes only that reservation, and unkeyed repository descendants are a failure.
- Admission first persists a `reserved` owner containing the wrapper process instance and permit weight. The wrapper then creates an execution container that cannot yet run repository code: on POSIX, a supervisor outside the repository execution group creates a blocked child as that group's leader; on Windows, an out-of-job supervisor creates a cryptographically random named Job Object with an owner-only DACL and kill-on-close, assigns a suspended root process, and retains the controlling handle. It persists the supervisor and container identities by transitioning the same owner to `active`, then signals/resumes the container.
- Ordinary spawned build/test descendants inherit that recorded container. If the wrapper dies while `reserved`, a blocked child observes pipe closure and exits; verified cleanup removes the reservation. If it dies after `active`, reclamation requires the recorded process group or Job Object empty. If wrapper and supervisor are both proven absent while the exact recorded Linux leader remains live, guarded recovery creates a new out-of-group supervisor that opens each enumerated member by `pidfd` and signals only through that stable handle, repeating through the bounded graceful/forced teardown until the group is proven empty. macOS has no equivalent race-free non-parent process handle, so supervisor loss with any live group member stays held with `SAFEWORD_TEST_CAPACITY_IDENTITY_UNVERIFIABLE` and the explicit locate, terminate, and retry procedure; recovery never uses check-then-`kill` or `killpg`. If the recorded leader is absent but members remain on either POSIX platform, the same fail-closed procedure applies. Windows Job Objects provide enforced containment; POSIX process groups do not prevent repository code from deliberately calling `setsid`, `setpgid`, or daemonizing.
- POSIX active state records the out-of-group supervisor PID and creation identity plus the execution PGID and its leader's creation identity. The supervisor remains alive until ordinary descendants exit; on wrapper-pipe loss it requests group termination, escalates to forced termination after one bounded monotonic deadline, and waits for proven group disappearance before exiting. Failure even after escalation leaves both ownership layers held fail-closed with recovery guidance. Recovery compares both recorded incarnations. Its first absent observation atomically marks the owner `reclaiming` with the exact recovery-process identity and an owner-record revision without returning capacity, then releases the state guard. Because supervisor, leader, and group membership require multiple OS reads, recovery waits a nonzero interval of at least one scheduler backoff before a second authenticated snapshot; this rejects a transient or torn apparent absence if the recorded container is present in the second snapshot. It then reacquires the guard and reclaims only if the owner record, revision, and marker are unchanged and the second snapshot again proves both exact instances and the group absent; unrelated state transitions do not restart the interval. A later caller leaves a marker owned by a live exact recovery process untouched; if that process is proven absent, it atomically adopts the marker, repeats the first absence observation, and starts a fresh interval. New admissions treat `reclaiming` weight as occupied throughout. A surviving recorded group member means the container is live, so waiters remain queued and may cancel normally. A stable creation-identity mismatch is a conclusive rebound: it proves only the recorded process instance absent and recovery never signals the new process. If the recorded PGID now belongs to a different leader, recovery treats the old container as absent only after proving the recorded leader absent and that no current group member predates the new leader; otherwise identity is unverifiable and capacity remains held. An unreadable identity fails closed with identity guidance. A live exact owner identity at either absence observation clears the marker. Tests inject the clock and platform observations rather than sleeping.
- Windows active state records the out-of-job supervisor PID and creation time, the random Job Object name, and the suspended root process PID and creation time before resume. On wrapper-pipe loss the supervisor explicitly terminates the job, queries its active-process count until zero or a bounded monotonic deadline, and only then closes its handle; failure to prove zero leaves ownership held fail-closed. Recovery reopens the exact owner-only named job when it exists and withholds capacity until its active-process count is zero. If the job no longer exists, recovery uses the same two-stage reclaim marker and exact root/supervisor creation-time absence proof. A name that exists with an unexpected identity/ACL, access denial, a live member, handle loss without provable emptiness, or unverifiable creation time fails closed; a random name is never treated as identity proof by itself.
- V1's POSIX capacity guarantee therefore covers non-detaching test/build tools. Deliberately detached descendants are unsupported and named as an evidence limitation; v1 does not claim it can discover or contain arbitrary escaped repository processes. If code escapes undetected, the recorded group can become empty and capacity can return while the escaped process remains active at any configured capacity. Safeword directs customers to disable detachment and use capacity one as an additional participating-wrapper safeguard; it never describes capacity one as containment, the escaped process as contained, or resulting overlap as safe.
- The scheduler state guard and checkout mutex each use the same process-instance validation contract for crash recovery. Cleanup removes only the exact staged owner identity; repository code cannot begin before the active container record is durably visible, and descendant teardown is proven before active capacity returns.
- Within one OS-user capacity domain, the checkout mutex lives in the same owner-only, no-follow, identity-pinned namespace as scheduler state. Its key is the opened checkout root's stable filesystem identity—device plus root inode on POSIX, volume serial plus root file ID on Windows—not a path string. The state guard also records a canonical-root-to-filesystem-identity mapping; every acquisition reopens and revalidates both sides before deriving the mutex key, then durably records the caller's checkout request before releasing the guard. If any checkout request, owner, waiter, or reclaiming weight references the mapping, a remount or identity change fails with `SAFEWORD_TEST_CAPACITY_IDENTITY_UNVERIFIABLE` instead of creating a second mutex. When no live state references it, the guard atomically replaces the stale mapping before deriving one new mutex; reset clears every mapping only after proving the entire domain idle. Failure to read or validate a stable unique identity returns `SAFEWORD_TEST_CAPACITY_PLATFORM_UNSUPPORTED`; network, overlay, or removable filesystems are unsupported unless they prove that contract. Thus supported aliases cannot create a second mutex for the same checkout. Its owner record begins with the exact wrapper identity and, before repository code is released, is durably linked to the same active execution-container identity recorded by the scheduler. If the wrapper dies while queued or reserved, exact wrapper absence permits recovery because repository code could not have started. If it dies after scheduler activation but before that durable link, the container remains blocked and recovery must prove it empty before removing either record. If it dies while active, the checkout mutex remains unavailable until the recorded process group or Job Object is proven empty; PID death alone never permits same-worktree overlap. Ambiguous, missing, foreign-owned, permission-unsafe, linked, or unverifiable mutex, wrapper, or container identity fails closed under the mutex transition guard. Cross-user or cross-process-identity-namespace serialization of a shared checkout is outside V1 because those domains cannot safely interpret one another's process evidence; status tells those domains not to target one checkout concurrently.
- Every run acquires its checkout mutex before entering the shared-capacity scheduler and releases shared capacity before the checkout mutex. It may hold the state guard briefly to bootstrap, look up, or revalidate the checkout mapping, but must release that guard before blocking on the checkout mutex; only after owning the mutex may it reacquire the state guard for scheduler admission. A failed or cancelled capacity wait releases the checkout mutex, and no code path waits on the checkout mutex while holding the state guard or acquires ownership layers in the opposite order. State-guard acquisition has a bounded monotonic deadline; expiry never breaks a live exact holder and returns `SAFEWORD_TEST_CAPACITY_BUSY` with retry guidance.
- If unsafe scheduler state prevents authenticated waiter removal, the failed caller leaves the exact bytes untouched. Status names the recorded-domain recovery procedure. After the underlying identity/access fault is repaired, guarded recovery may prune only a ticket whose exact process instance is proven absent; while identity remains unverifiable, status and reset fail closed without mutation until the operator locates the recorded domain and proves it idle.
- Canonical configuration is per OS user, machine, and supported process-identity namespace. Its root comes from an OS account API rather than `HOME`, `XDG_CONFIG_HOME`, `APPDATA`, or another process environment value: the account-database home plus a fixed Safeword state suffix on POSIX, and the user's Known Folder API result plus a fixed suffix on Windows. The root is canonicalized without following an existing unsafe leaf, and state records its canonical identity; a later mismatch fails closed instead of initializing another domain. Active scheduler state uses a stable owner-only namespace derived from the OS machine identity (`IOPlatformUUID` on macOS, machine ID on Linux, or `MachineGuid` on Windows), the OS user ID/SID, and Linux PID-namespace inode where applicable. Distinct OS users and Linux PID namespaces are separate capacity domains and must not run participating wrappers against the same checkout concurrently; non-Linux containers that share a user profile/state root while process namespaces differ are unsupported and must not target that root concurrently. Status discloses these boundaries without claiming a distinct domain it cannot derive.
- Configuration and active state carry a schema version. Corrupt, unreadable, permission-unsafe, or newer incompatible state fails closed with a recovery action and never bypasses the scheduler; a migration may run only while the scheduler is idle.
- An owner identity combines PID with the operating system's process creation identity on macOS, Linux, and Windows. Multi-read identity is accepted only as one authenticated, internally consistent snapshot; process exit/reuse or a machine/process identity change between reads fails closed. A stable snapshot that finds the PID bound to a different creation identity positively proves the recorded instance absent; reclamation still waits for the recorded execution container's platform-specific emptiness proof. If creation identity cannot be verified, Safeword fails closed instead of reclaiming by PID or elapsed age.
- After implementation removes feature-level `@wip`, required Linux, macOS, and Windows CI jobs run scenarios tagged with their exact `@platform-linux`, `@platform-macos`, or `@platform-windows` tag, respectively, including scenarios carrying more than one applicable platform tag. Each job fails if its tag expression selects zero scenarios. Injected adapter tests remain separate and cannot satisfy a missing required native job; ordinary required-check conclusions provide the evidence, with no custom attestation format or second evidence-state machine.
- Linux identity uses boot ID plus `/proc/<pid>/stat` start-time ticks; Windows uses the process creation time associated with the PID; macOS reads `kinfo_proc.kp_proc.p_starttime` through `sysctl(KERN_PROC_PID)` at microsecond precision. Missing, malformed, permission-denied, or internally changed readings fail closed.
- If machine or user identity becomes unavailable, changes unexpectedly, or conflicts with persisted configuration after scheduler initialization, Safeword refuses new admission and reports how to locate and drain the recorded domain; it never switches guards while checkout requests, owners, or waiters may exist. The legacy capacity-one mutex is available only before current-protocol initialization or after the prior domain is located and proven idle through its recorded identity, followed by an explicit reset.
- Scheduler and configuration errors exit nonzero, start no repository process, and emit a stable machine code plus `safeword project test-capacity status` as the first recovery command, except that a missing or integrity-invalid required native helper emits its exact helper repair command directly because status requires that same helper. A failing status command instead prints the canonical domain path it attempted plus the applicable direct repair, locate-and-prove-idle, exact-member teardown, or archive procedure; it never tells the operator merely to rerun status. When the domain authenticates but a recorded process identity does not, status still emits that authenticated domain ID and its direct recovery procedure. When the domain itself cannot authenticate, status emits no reset token and gives the direct locate-and-archive procedure instead. Combined faults are evaluated in this order: invalid syntax or value; unsafe artifact/schema/durability; unverifiable identity; unavailable platform containment; busy checkout request, owner, waiter, or lost update. Error codes are `SAFEWORD_TEST_CAPACITY_INVALID`, `SAFEWORD_TEST_CAPACITY_STATE_UNSAFE`, `SAFEWORD_TEST_CAPACITY_IDENTITY_UNVERIFIABLE`, `SAFEWORD_TEST_CAPACITY_PLATFORM_UNSUPPORTED`, and `SAFEWORD_TEST_CAPACITY_BUSY`, respectively. Status exits zero only when the authenticated domain and every recorded request/owner/waiter identity are verifiable; any unverifiable recorded identity returns `SAFEWORD_TEST_CAPACITY_IDENTITY_UNVERIFIABLE` with direct recovery guidance. Reset permits mutation only after that recorded domain is proven idle; a syntactically valid but mismatched expected domain is invalid input, while an unreadable identity is unverifiable. Non-cancelled public wrappers forward the downstream collaborator's exact numeric exit status on every platform; Safeword-initiated cancellation is a distinct terminal signal rather than a recoverable scheduler error, takes precedence over simultaneous scheduler faults, exits 130 at every queue stage, and emits `SAFEWORD_TEST_CAPACITY_CANCELLED` without requiring a status recovery command, distinguishing it from a downstream exit 130. Deterministic termination fixtures predeclare arbitrary numeric statuses such as 137 or 143, without making POSIX signal-name semantics part of the cross-platform contract.

- Kernel-released locks alone cannot represent a durable weighted FIFO queue or retain checkout ownership after the wrapper dies while its descendants are still active. V1 uses OS locks for short state-guard exclusion, while durable owner/container records carry those two load-bearing semantics; it does not replace the queue with PID polling.
- FIFO fairness remains in V1 because broad-run starvation is part of the reported issue cluster: capacity sharing without the queued-broad barrier would make short checks responsive by allowing full verification to starve.
- The terminal authenticated-idle procedure also applies to a permanently unverifiable recorded owner or waiter: independently prove every recorded process and execution container absent, archive and remove only that domain's unsafe artifacts, then initialize capacity one. No reset or byte edit may substitute for that external proof.
- The bounded-capacity guarantee covers participating current-protocol sessions only; it does not claim to detect, exclude, or control a legacy process. Mixed old and new package-test wrappers cannot safely share capacity because old clients do not understand permits. Before using a legacy wrapper, the customer must return the current protocol to capacity one and wait for it to become idle. Continuous mixed-version execution and an atomic legacy-to-current handoff are explicitly deferred from v1.
- V1 does not intercept arbitrary standalone build, test, or repository commands that bypass the current package-test wrapper. Within one OS-user capacity domain, same-worktree serialization covers participating wrappers and every build/test descendant they spawn; extending the checkout mutex to unrelated commands or distinct OS-user domains is a separate integration surface.

## Required Next-Phase Evidence

- Test harness proof terms—including predetermined statuses, trusted CI attestations, independently verified identities, and proven-empty containers—must be fixed or authenticated before the action under test. A step may not derive its expected evidence from the observed outcome it is meant to verify.
- Concurrent process-level scenarios must use the real package-test wrapper and build/test collaborators, not an isolated scheduler adapter.
- Native real-CLI scenarios run serially inside a disposable Linux, macOS, or Windows runner account whose canonical Safeword domain is dedicated to that scenario job. The harness may seed or corrupt only that account's actual canonical artifacts before any wrapper starts and discards the runner afterward; production exposes no state-root override or environment-derived isolation seam.
- Process evidence is keyed by exact wrapper process instance, FIFO ticket, container identity, and command ID. The harness records monotonic sequence numbers for admission, descendant creation, build/Vitest start and exit, ownership release, and wrapper terminal exit; every success/failure assertion names the command's terminal status and proves no unaccounted descendant remains.
- Filesystem crash barriers self-check their ordering by having an independent observer open and verify the named side effect only after the underlying syscall-return event; a nearby harness event is not accepted as proof.
- Scenarios must cover focused batching, FIFO broad exclusivity, cancellation at every queue stage, wrapper death before and after container activation, supervisor exit, surviving descendants, group disappearance, PGID reuse, same-worktree serialization, capacity validation, corrupt state, and capacity-one recovery.
- Platform contract coverage must exercise Linux, macOS, and Windows identity/container seams; any platform that cannot prove the required primitive stays at capacity one with the limitation named.
