# Impl Plan: Review complete branch changes before builders finish

**Status:** planned
**Planned on:** 2026-10-23

## Approach

The shared Safeword CLI owns Git inventory, bounded review dispatch, path accounting, and a signed branch-review result. The existing BDD implementation-exit action invokes that CLI operation with the active ticket; it does not accept a caller-selected file list or base revision. The existing phase-change gate checks the saved result immediately before changing `ticket.md`. The later done check validates reviewable content again. The host integrations call the same CLI decision, with their existing hard versus advisory enforcement limits.

The riskiest assumption is that reviewer prose will not accidentally determine whether inspected paths receive coverage credit. A real approving review already returned unstructured warning findings and left 25 authored paths uncredited. Prove that an independent approved pass with zero findings or unstructured non-blocking findings credits inspected paths, while a `request_changes` pass with an unstructured finding remains visible, uncredited, and blocking. Independently enumerate expected paths with Git, then compare exact path sets to reviewed plus omitted paths; a generated report cannot be its own completeness oracle.

Proof strategy (the 22 scenarios share these behavior groups):

| Behavior and scenarios | Owner and primary proof | Real boundary and confidence limit |
| --- | --- | --- |
| Merge-base inventory, caller cannot shrink it, renamed/deleted/ignored committed paths | CLI inventory integration | Temporary Git repository through real `git`; proves path identity and base selection, not reviewer judgment |
| Ticket-aware, cross-file, prioritized findings | Review coordinator integration plus the independent branch review | Real packet assembly and controlled reviewer process prove context, typed finding attribution, and credit for approved passes with zero or unstructured non-blocking findings; live reviewer judgment remains a separate semantic limit |
| Current complete review advances; stale authored work and combined phase/goal writes block; routine records do not; identical-content commit stays current | Gate integration | Real CLI result and phase-write check with a ticket fixture; proves exit wiring, not every host's native hook registration |
| Each of four local hosts checks phase exit and the later closing status edit | One wiring proof per Claude Code, Codex, Cursor, OpenCode CLI entry point, plus a current-review close case | Invoke installed host adapters with the real shared gate and mock only the native process boundary; cloud/advisory behavior is disclosed separately |
| Partial acknowledgement and missing-acknowledgement refusal; empty inventory needs skip | Gate and Stop integration | Receipt-bound acknowledgement and review-ID-bound skip, including stale skip refusal and the exact omitted-path disclosure; cannot prove human comprehension |
| Generated/oversized/secret-sensitive path, dirty work, failed pass, stale report | CLI review integration | Real inventory and bounded packet assembly, controlled pass failure; exact-set check independently detects omissions; cannot promise full secret detection or semantic review of omitted bytes |
| Plain-language next action | CLI result contract assertion plus a short NTB-facing read-through | Checks visible words and action, not actual user understanding |

Each behavior group needs a discriminating assertion that fails if its behavior is removed; retain the independent Git path-set comparison for the whole inventory. The host proof invokes each real adapter process with a host-shaped payload; only the external host process is simulated.

Affected surfaces: Safeword CLI gets an end-to-end command proof; Claude Code, OpenAI Codex, Cursor, and OpenCode CLI each get a host entry-point wiring proof. OpenCode Desktop and Codex Cloud remain advisory where the host cannot block. The existing PR conversation is outside this change.

### Persona consequences

- **Technical Builder:** Can see exact Git scope, path accounting, reviewer provenance, and stale reason. The explicit agent acknowledgement permits progress on partial coverage but cannot turn an omitted file into reviewed evidence. Retry regenerates a receipt for current work.
- **Non-Technical Builder:** Sees complete/partial/none separately from current/stale, the missed paths, findings, and one concrete next action. No new user approval is introduced. The message must say when the reviewer lacked evidence; automated wording cannot establish that the user understood it.

### Current and target truth

- **Implemented fact:** `review run quality-review` accepts caller-selected targets and bounded packets; BDD asks the agent to review the whole diff; phase stamps attest to coordinator reviews. The oversized `bun.lock` projection is a narrow existing exception. Replay code now contains a branch-review command, signed record, acknowledgement, marker, and phase gate; these are implementation in progress, not accepted proof.
- **Available proof:** Existing focused integration tests and the BDD proof lane exercise review and gate paths. Final branch review and completion evidence are checked during execution.
- **Proposed decision:** Add branch-scoped inventory and result, preserve the existing general quality-review contract, and require the result at implementation exit.
- **Pending human authority:** The user approved this behavior scope. Implementation Plan and Execution Plan review/approval gates still apply; no merge or release is authorized by this plan.

The shared constraint is recorded in [Safeword Architecture](../../../ARCHITECTURE.md#branch-scoped-implementation-exit-review). A new CLI operation is valid only for an active BDD ticket. It accepts the active ticket identity, never arbitrary target paths, a base, or a per-run integration ref. The project-owned integration-ref configuration is resolved as described below. It returns a typed result with base, head, actual reviewer, prioritized findings, reviewed and omitted paths/reasons, `freshness: current|stale`, and `coverage: complete|partial|none`. Invalid ticket/ref, unavailable Git, and lost review passes are distinct failures or omissions; none may produce complete coverage. It is idempotent for the same content and ticket goals. Concurrent review runs are separate signed jobs; only a current result can satisfy exit. A partial result requires an acknowledgement bound to its receipt identity and exact omitted set, recorded by the agent and disclosed to the user. A `none` result may use the existing reasoned skip path only with a current sealed result for this ticket; a skip note without that result cannot satisfy exit. Gate proof refuses a skip with authored work and no qualifying result. Existing callers of generic `review run quality-review` remain compatible.

### Branch result contract

**Public CLI contract.** Catalogue `review branch <ticketId>` as a mutating command with declared network use: it fetches the project-selected integration branch, writes a signed local review job, and records `branch_review_exit_id` in the active feature ticket. `--offline` or a failed network fetch seals a signed baseless `none` result and updates the ticket marker. It credits no paths and reports that the branch path list is unavailable; a current result permits only the existing review-ID-bound reasoned skip with disclosure. A usable local ref is never credited as fetched scope. Catalogue `review branch-check <ticketId> <implement|verify>` as read-only and `review branch-ack <ticketId> <reviewId> --reason <text>` as the acknowledgement/disclosure mutation. A current complete result is `healthy` (exit 0) when every returned pass is approved, even if an approving pass reports warning or info findings; those findings remain visible for the builder to assess. Partial, none, stale, or any returned `request_changes` verdict is `action_required` (exit 2), with coverage, freshness, omissions, and a concrete next action in JSON and the one-line human verdict. Invalid syntax or ticket yields an explicit error or action-required result and never a successful review. Only the separate `branch-check` gate may return healthy for a current acknowledged partial result or the existing reasoned-skip route.

**Finding shape.** The branch result adds `branch_findings[]` with `affected_behavior` (ticket rule or scenario reference plus a short description), `related_paths` (nonempty paths from the credited review pass), `consequence` (what fails for the user), and `priority` (`high`, `medium`, or `low`, sorted in that order). It also retains the coordinator's existing `severity` and `message` for compatibility; `error`, `warning`, and `info` map to high, medium, and low respectively. The coordinator's strict two-field reviewer finding schema is unchanged. For this branch operation only, the reviewer is instructed to put the three named details in its message using a small structured convention; the branch adapter parses and validates them before adding typed findings. An independent approved pass credits inspected paths even when it has no findings or only unstructured warning/info findings; raw findings remain visible and are never invented as typed findings. An unstructured `request_changes` finding leaves that pass uncredited, names its paths as omitted, and blocks exit. A structural integration test proves all three verdict/finding combinations, required typed fields, path membership, and ordering with a controlled reviewer. This proves transport and accounting, not the reviewer's ability to detect a semantic gap.

The observed review on this ticket returned approving findings without that structure for 25 authored paths. Under the revised rule those paths receive inspection credit while the raw warnings remain visible. Typed attribution is claimed only for parseable findings; reviewer judgment and the meaning of raw warnings are not certified by the structural tests.

**Zero reviewed paths.** Coverage is `none` whenever the inventory is empty or no authored path was credited as reviewed, including all-dirty, all-generated/sensitive, and all-failed-pass branches. The signed result retains every changed path as a named omission and says no branch work was reviewed. It cannot use partial acknowledgement. A current sealed `none` may use the existing substantive reasoned-skip route only if no returned pass in that same job requested changes; the gate surfaces every omission and the skip reason rather than claiming a clean review. A malformed but returned `request_changes` finding remains visible and blocks even a `none` skip. A fresh latest job with no request for changes can supersede an earlier job's finding, so its explicit skip can still bypass that earlier finding. This escape-hatch tradeoff is not represented as reviewer approval. Gate proofs cover all-withheld and all-dirty `none` results with no returned request for changes: neither can advance ordinarily or through partial acknowledgement, and each advances only with a recorded reasoned skip and visible omission disclosure. Another proof refuses a same-job `none` skip after an uncredited `request_changes` pass and displays its raw finding.

**Verdict and packet credit.** Coverage says which paths the reviewer could inspect; it does not waive findings. Preserve every returned verdict and raw finding in the signed result, including those from a pass whose finding attribution failed validation and whose paths were therefore omitted. Any `request_changes` verdict from any returned pass blocks ordinary exit and partial acknowledgement, regardless of path credit or finding format. A partial acknowledgement covers only missing paths, never a reviewer request for changes. A sealed `none` result carries no credited passes and may use only its qualifying reasoned-skip route. Gate proofs refuse a current acknowledged partial result after a credited or uncredited pass requested changes, and show the raw finding in the report.

For added and modified paths, the reviewer receives the full current file content and ticket context before the path can be credited. For a rename, the destination's current content may be credited, while the source path is named as omitted with reason `deleted or renamed source`; a deletion has no current bytes and is likewise omitted. Generated, sensitive, unreadable, oversized, dirty, and failed-pass paths remain named omissions. A pass that lacks representable ticket context cannot credit its paths. The existing oversized-lockfile baseline patch is a separate generic quality-review representation and does not make deleted branch paths reviewed. Rename/delete proofs assert the exact reviewed and omitted classifications, not only path names.

**Bookkeeping-only dirty paths.** Project each path before classifying dirty work or comparing the exit path set. If an uncommitted change alters only excluded bookkeeping, such as `branch_review_exit_id`, a Work Log disclosure, ledger checkboxes, or Delivery Checklist progress, that path is absent from the reviewable dirty set and cannot make coverage partial or the saved review stale. If the same file also changes a goal-bearing field, retain it as dirty. A gate proof seals a review, writes the marker and disclosure without a commit, and confirms implementation exit stays current.

**Dirty coverage.** Nonignored, reviewable staged, unstaged, and untracked paths are named in `dirty_paths` for diagnosis and in `omitted_paths` with the reason `uncommitted work`; they are never credited as reviewed even when their current bytes are visible in a reviewer packet. Thus any dirty authored path makes coverage partial, and the exact omission digest, acknowledgement, generated Work Log disclosure, and builder-facing next action all include that path. Committing it and running a fresh review is the route to complete coverage.

**Scope source.** Only project configuration may name an integration ref; a run cannot override it. The configured value must be a named `refs/remotes/<remote>/<branch>` ref, not a SHA, relative revision, local topic branch, or `HEAD` expression. Without one, choose `origin` when present, otherwise the sole remote; multiple non-origin remotes are ambiguous and yield a sealed baseless `none` with a concrete reason. A repository with zero remotes follows the same path. The explicit review command asks that remote for its symbolic HEAD to identify the remote default branch; never use the topic branch's upstream tracking branch. If remote HEAD is structurally absent or ambiguous, coverage is `none` rather than a guessed main/master. The explicit review command fetches that exact remote branch before inventory and records the fetch time. A structurally missing ref or missing common ancestor yields coverage `none` at review time; offline mode and transient network failure create a baseless `none` receipt that requires a review-ID-bound reasoned skip. For a result with a base, the phase-write gate does not fetch: it checks the saved ref name and local remote-tracking ref, recomputes `git merge-base` with current HEAD, and compares the base with the signed result. A missing local ref blocks exit for that result; a newer locally observed remote tip with the same merge base does not stale it. After implementation exit, a moved integration tip that contains the signed reviewed head also leaves the result current if the authored-content and ticket-goal projections are unchanged; this covers a push or merge of already-reviewed work without treating new work as reviewed. For a sealed baseless `none` result, the missing-ref/base check is waived so the existing reasoned-skip route can work. Its separate freshness identity is specified below. The gate reports the saved fetch time when a fetch succeeded so the builder can see the currency limit while offline. This excludes commits already merged into the fetched integration branch from the ticket-work claim; a temporary Git-remote proof merges an upstream commit, fetches, and shows it absent from the inventory. A second proof makes the topic track `origin/topic` and confirms the default is still `origin/main`. Work merged earlier cannot be retroactively claimed as reviewed. The existing oversized-lockfile baseline fallback remains confined to that representation and cannot choose this branch-review scope.

Reject a configured remote-tracking ref that names the current branch itself or its configured upstream when that ref is not the remote default integration branch, including a locally renamed topic still tracking `origin/<topic>`; it would cut off earlier ticket commits. An upstream pointing to the remote default integration branch, such as `origin/main`, is valid and must not be rejected merely because it is the upstream. Work directly on the integration branch is valid: review local unpushed commits against the fetched remote-tracking tip; if the exact inventory is empty, seal `none` with an explicit no-change report and allow the existing reasoned-skip route. Earlier work already pushed to that integration branch lies outside the merge-base-to-HEAD scope and is not claimed as reviewed. A rejected self-ref is an action-required configuration error, not a structurally missing base: seal no result, write no ticket marker, and offer no reasoned-skip route. Bind whether a valid ref came from configuration or remote-default discovery, and the relevant configuration content, into the signed result. A configuration edit after review makes the result stale at exit and done, even if the old merge base still resolves. The gate reads local configuration and Git state only. Proofs configure `origin/<topic>` after renaming the local branch and assert an error with no saved job or marker, make a topic track `origin/main` and confirm review still runs, and review local unpushed work on `main` against `origin/main` while an unchanged `main` yields a sealed, skippable `none`.

**Configuration failure classification.** Malformed config JSON, a malformed `branchReview` object, a non-string or non-`refs/remotes/<remote>/<branch>` configured value, and a configured ref absent after fetch are action-required configuration errors: no result is sealed, no marker is written, and no skip can use them. A valid configured or discovered ref whose history has no common ancestor, or a remote whose default symbolic HEAD is structurally unavailable, may seal a baseless `none` with the concrete reason. Offline mode and transient fetch failure seal a baseless `none` with no reviewed paths and an explicit unavailable path list, even if a local ref exists. They do not record a successful fetch time. CLI proofs exercise malformed JSON, invalid value, absent configured ref, unavailable remote HEAD, and fetch refusal separately.

**One exit review.** For a feature's implement-to-verify transition, the branch-review result replaces the generic `quality-review` phase stamp as the review evidence. The existing `/quality-review` whole-ticket workflow invokes `review branch` once; it does not dispatch a second generic review at that boundary. The shared branch-result gate enforces the signed receipt directly. Generic phase stamps continue for other phases and non-feature tickets; older generic implementation stamps cannot substitute for branch coverage after this feature is installed. `none` still uses the existing substantive reasoned-skip record in addition to the sealed `none` result. Its skip stamp cites the sealed branch-review ID; the trusted CLI checks that exact ID at phase exit and at completion, and returns every omitted path in the disclosure. An earlier skip cannot authorize a later review job. Before calling the trusted checker for a ticket phase Write/Edit, the hook projects the **proposed post-write ticket content** using the same goal-neutral exclusions as the signed ticket projection and refuses any goal-bearing difference from the on-disk content. Thus one edit cannot both advance the phase and change reviewed goals; the builder must change the goal, rerun review, and then advance.

**Reviewable identity.** At exit, require the current HEAD revision to equal the signed reviewed head exactly. Also compare integration-ref name, computed merge base, exact committed path set and statuses, staged/unstaged/untracked nonignored path set and reviewable content, and ticket-goal projection. A newer integration tip with the same merge base is harmless. A content-identical amend or rebase before exit is stale and requires another review; a real Git proof covers that case. The goal projection includes `ticket.md` `scope`, `out_of_scope`, `done_when`, Product Plan jobs and Rules in `spec.md`, all scenario `.feature` files declared by the ticket, and the headings and behavioral obligations in `test-definitions.md`. Project or ticket files not expressly classified as routine bookkeeping are reviewable by default. At exit as well as afterward, compare ticket file content through a projection that excludes only frontmatter `phase`, `status`, `last_modified`, `phase_anchors`, and `branch_review_exit_id`, plus Work Log entries, review acknowledgement, `${ticketDirectory}/verify.md`, and files under `${ticketDirectory}/evidence/` or `${ticketDirectory}/audit/`. These two directories hold post-review evidence only; all other authored paths remain reviewable. A phase edit that adds its required `phase_anchors` entry keeps the review current; a body or goal-field edit remains reviewable. In `test-definitions.md`, checkbox state and commit/skip annotations are progress, while a changed scenario or obligation is reviewable. In `execution-plan.md`, Delivery Checklist progress cells (Disposition, Evidence class, Revision, and evidence text) are progress; a commit that changes only excluded bookkeeping or leaves the authored-content projection identical does not stale review; changed tasks, proof requirements, and accepted obligations remain reviewable. The gate proof changes these progress fields after review and confirms currency, then changes a goal-bearing field and confirms staleness. The full exit snapshot means all reviewable authored bytes and path identities, not a raw byte hash of self-generated bookkeeping. An edit to an excluded file that changes a goal-bearing field is reviewable. A proof writes the partial acknowledgement and generated Work Log disclosure after review and then advances without a false stale result. After exit, recompute the full authored-content inventory from the **signed original merge base**, not the current merge base or only the signed path set, and compare it with the sealed content projection and ticket goals. This catches a newly added file even when the reviewed head has since been pushed into the integration branch. Phase bookkeeping never causes a loop. A new commit whose content projection is identical retains current freshness; changed authored bytes make the result stale. A moved merge base is allowed at done only when the new integration tip contains the signed reviewed head and the full original-base projection remains identical. A real-Git proof reviews unpushed work on `main`, exits implementation, pushes to `origin/main`, then adds and pushes a new authored file; done must refuse the old receipt. The report retains its original coverage and omissions when stale.

Because exit binds the exact HEAD, committing only the marker or generated disclosure before the phase write also makes the result stale; the builder-facing next action is to rerun the branch review after that commit. Keep this bookkeeping uncommitted until the phase write when possible. After exit, content-identical commits are harmless under the projection rule above.

**Baseless `none` identity.** When integration scope cannot be resolved, seal the ticket ID, HEAD revision, reviewable staged/unstaged/untracked path and content projection, ticket-goal projection, and the concrete unavailable reason in the signed result. At implementation exit, compare the current HEAD and those projections with the sealed values; any later commit or reviewable edit makes this result stale. After exit, use the sealed HEAD as the comparison baseline for committed and working-tree changes and compare the projected authored content and goals, rather than requiring the same HEAD. Thus a commit containing only routine Work Log, verification, or phase records remains current, while a later authored commit or goal edit becomes stale. Only a current sealed `none` result plus the existing reasoned-skip record can advance, and the result must still say that no branch work was reviewed. A gate proof makes the remote HEAD unavailable, seals `none`, advances with a reasoned skip, then adds an authored file and confirms that the same result is stale and exit is refused. Another proof commits only routine bookkeeping after that exit and confirms done can proceed with the unchanged original result; if authored work changes, a fresh baseless result and a new substantive skip can complete a local-only ticket with explicit unreviewed-work disclosure.

**Replacement at completion.** After implementation exit, a fresh review may replace the ticket marker when it credits reviewed paths: current complete coverage with approved passes, or current partial coverage with a signed acknowledgement and exact disclosure. A fresh, current, sealed `none` may also replace the marker at done, whether a base exists or not, only with a new substantive skip bound to that exact review ID. Its disclosure names every current omission, says no branch work was reviewed, and carries any earlier superseded requested-changes finding; it is never reviewer approval. A same-job `request_changes` verdict blocks the skip. An unacknowledged partial result cannot close the ticket. Gate proofs change authored code during verification on a host without a reviewer, then require a fresh `none` result and new skip before done; the earlier skip cannot carry forward.

**Acknowledgement and result selection.** The agent records a partial-coverage decision through a typed local CLI operation that writes an authenticated sidecar in the existing review-job store, keyed by review ID, ticket ID, exact omitted-path digest, and decision text. The coordinator's signed review job remains immutable. The sidecar is written atomically with the store's existing integrity mechanism; hand-edited ticket notes do not satisfy the gate. It is outside the reviewable snapshot and cannot stale its own review. The exit validator reads and verifies both records, matches the omission digest, and requires disclosure of the same omissions in the implementation-exit summary. `none` cannot be acknowledged into partial or complete. If a process dies before the review result is sealed, there is no qualifying result; if it dies before acknowledgement is sealed, partial coverage remains unacknowledged. Retries create independent review jobs. Select the latest completed review job for this ticket by the coordinator's durable completion order, then validate it; do not fall back to an older result when the latest is stale, partial, or failed. An acknowledgement is idempotent only for its exact review ID and omission digest. Same-user local job-store modification remains within the existing trusted boundary, not a claimed hostile-user protection.

An authenticated record for another ticket does not participate in selection. A parseable but damaged record claiming this ticket fails closed rather than revealing an older result; a damaged record clearly belonging to another ticket is skipped. An unparseable record has unknown ownership and makes the gate action-required until repaired, so it cannot create a false legacy path. The ticket marker must still match the latest valid result ID; it never overrides a newer job. Prove a valid result survives a damaged other-ticket record, and prove same-ticket or unknown damage cannot turn a reviewed ticket into `legacy_uncovered`.

The ticket marker must name exactly that latest sealed result. A crash between sealing and marker write or two concurrent runs that leave them different fails closed; rerun the review to repair the marker. Branch path credit uses the accepted 2026-08-02 class-1 **agent-identity** contract: a sealed `cross-agent` pass from a different reviewer process credits inspected paths when it approves, or when it requests changes with attributable findings. Approval is a separate requirement for advancing. The proposed 5F5ZZA verified-model/not-weaker comparison is scoped to planning review and does not classify this quality-review kind; the branch command uses the coordinator's actual non-planning independence result. Under `prefer`, a reduced or failed pass leaves its paths omitted; under `require`, it also blocks the required review; under `off`, no independent pass runs and coverage is `none`. Cursor's default coordinator route is unsupported without configured reviewers, so its branch result is likewise `none` with exact omitted paths. These are visible limitations: the agent may use the approved reasoned-skip route, disclose that no branch work was reviewed, and never call the result complete or independent. The proposed planning-only reduced-independence ladder does not extend this class-1 quality review. Host proofs check the credited cross-agent route and the honest `none` route rather than claiming default independent coverage everywhere.

**Disclosure surface.** The typed acknowledgement operation generates a fixed plain-language disclosure from the signed omitted-path set and writes it to the ticket Work Log, as well as printing it in the CLI result. The agent supplies only the reason to continue, not the omission text. The phase-write validator requires the authenticated sidecar and the exact generated Work Log disclosure before advancing; it then returns the same disclosure in its gate result for the host to surface. A crash between the sidecar and Work Log writes leaves the gate unsatisfied; repeating the operation repairs the missing copy without changing the review. Chat may repeat the message but is not the evidence. An integration proof removes one omission from the Work Log disclosure and must observe exit refusal.

**Host and rollout limits.** Local Claude Code, Codex, Cursor, and OpenCode CLI phase-write adapters call the same validator; each must have one real registration-to-gate proof in addition to focused adapter tests. The later freshness check runs both at the `verify` to `done` phase write and at the separate `status: done` closing edit when the prior phase is `done`, through the same shared pre-tool gate in all four local adapters. Each host gets a real stale-close proof. Cursor runs its done-evidence check first and then continues through the shared branch gate; it also gets a current-review close proof. The branch-review command remains available during `phase: done` and records a verification-phase review, so a late correction can earn a fresh result before closing. Claude Code's Stop hook can itself mark `status: done` after the phase edit, so it must call the same branch-result validator immediately before that write and hard-block completion when marked-ticket evidence is missing or stale. This closes the interval where authored work could change after the phase edit. Other host Stop surfaces call the validator at their completion boundary and block where supported; advisory surfaces report the stale result and cannot claim enforced completion. Older installed bundles do not gain or forge coverage retroactively; mixed-version hosts may still advance without the new gate and must be reported by status/doctor rather than shown as covered. An in-flight implementation ticket runs this review at its next implementation exit after upgrade. The explicit branch-review command writes a goal-neutral `branch_review_exit_id` to the ticket when it seals a result; the implement-to-verify gate requires that marker to match its signed result. On later ticket edits, the shared pre-tool gate refuses marker removal and permits replacement only with a newly sealed signed result for that ticket; this lets a fresh review in verification repair missing or stale evidence. The done gate also refuses a marker that does not match its signed result. A ticket already in verification at upgrade has no marker and no local branch-review job: its verify-to-done gate retains the prior behavior and status/doctor discloses that branch coverage was not established. If the marker is missing but any local branch-review job exists for the ticket, done fails closed instead of treating it as legacy; rerun review to repair the marker. A marked ticket whose local result is missing also blocks done and must run a fresh review in verification. If both marker and local job store are lost, this local same-user evidence cannot distinguish the ticket from a pre-upgrade one; the status/doctor disclosure is a confidence limit, not a claim of hostile-user tamper resistance. Gate proofs remove the marker through each supported host edit, remove a marked ticket's local result, and exercise the no-marker/no-job upgrade case. Arbitrary shell writes are outside the editor-hook enforcement boundary; the later done check still detects a missing marker when its local job remains. A Stop proof changes authored bytes after the phase edit and confirms completion is refused. The cross-file finding example uses two small related files that fit one bounded pass; broader cross-pass semantic completeness is not claimed.

### Data applicability

Data applicability: The review result is a new local, ticket-scoped evidence record, not a remote store.

- **Purpose:** Preserve exactly what a branch review covered so a later gate can validate a claim.
- **Store and model:** Reuse the coordinator's signed job/receipt store; add a versioned branch-coverage payload rather than a second database. Older jobs remain valid for their original review meaning but cannot claim branch coverage.
- **Schema and relationships:** Bind ticket identity, integration ref/base, reviewed content identity, goals identity, reviewer provenance, path inventory, omissions, findings, and acknowledgement to the result ID. A goal-neutral ticket marker records the result used at implementation exit. Reject duplicate or missing path classifications.
- **Source of truth:** Git supplies branch and working-tree paths; current ticket/scenario files supply goals; coordinator-signed result supplies reviewer evidence. The report is derived, never the path oracle for its own completeness.
- **Ownership and access:** Local same-user CLI writes; hook reads through CLI verification. No new public permission or remote read route. Existing reviewer dispatch may receive bounded nonsecret repository evidence.
- **Identity and integrity:** Recompute base and exact path set at exit; bind content/goal digests and omission set to the signed job. Stale is independent of coverage.
- **Cross-system flow:** CLI to reviewer via existing neutral packet; CLI to host hooks via typed local result. No customer data or credentials are sent as review context.
- **Lifecycle and retention:** Reuse current review-job retention and validation. A new review supersedes an older result for exit; earlier requested changes are disclosed only while their signed jobs remain in the local store. Cleanup may remove old jobs, so the disclosure must say its history is limited to retained jobs. A marked ticket whose current job was deleted needs a fresh review before done; if both marker and job store are lost, the documented legacy confidence limit applies. No new retention policy or deletion record is introduced.
- **Migration and backfill:** No backfill. Existing review stamps do not turn into branch-coverage receipts; the new implementation-exit gate applies after installation. Tickets already in verification have no exit marker and retain their previous done path. A marked ticket needs its signed result or a fresh review before done.
- **Compliance:** No new privacy, residency, or audit obligation identified beyond existing local review packet policy; excluded sensitive paths remain named without content.
- **Rollback:** If the new exit gate causes trouble after release, disable that enforcement in a follow-up patch while retaining the catalogued branch-review command and typed result fields. The command may return a typed unavailable result until repaired; do not remove a public command or silently reinterpret `complete`, `partial`, and `none`. Existing result payloads remain readable and need no destructive cleanup.

## Known deviations

For a later `none` skip, inspect every older retained signed job for this ticket in durable completion order and include each earlier `request_changes` finding in the exit and done disclosure, deduplicated by message. An intervening approved job does not erase a retained finding or assert that it was resolved. The disclosure explicitly limits its history claim to retained local jobs; a pruned job cannot be reconstructed or claimed as checked. If an older retained record for this ticket is damaged, or its ownership cannot be read, the skip is ineligible until the store is repaired; a damaged record for another ticket is irrelevant. Gate proofs show a retained earlier finding at both exit and done and refuse a skip when its retained record is damaged.

The branch-specific result replaces the generic phase stamp only for feature implementation exit because that stamp witnesses a reviewer verdict, not a complete Git inventory. Other phases and ticket types retain their stamp semantics. The shared branch-result validator runs at phase write and completion. Premortem: an older generic stamp could appear valid while branch coverage is stale; the feature exit must consult the branch result directly and never treat that stamp as sufficient. Revisit if all review kinds later adopt path accounting.

The existing reasoned skip remains an explicit builder escape hatch. If a later `none` job supersedes an earlier requested-changes review, the agent can record a substantive skip and leave implementation with disclosed omissions and the earlier finding. This preserves the Product Plan's `none` route and avoids treating prior findings as an unbounded hidden gate; the result must say no branch work was reviewed, and the skip is not an approval.

Host limitation: Cursor without a configured opposite reviewer, and any host with cross-agent review switched off, can only produce `none` coverage. The accepted scenario allows the agent to proceed with a substantive, review-ID-bound skip and exact disclosure; it does not claim a full review occurred. Supporting a reduced-independence path-credit contract for class-1 reviews would require a separate architecture decision and coordinator work.

Reviewer-strength limitation: this branch review follows the coordinator's existing class-1 cross-agent identity contract, which proves a different process and actual reviewer but cannot always verify that reviewer's model is no weaker than the author. A credited pass therefore proves cross-agent review, not model-strength parity; this weakens confidence for the Non-Technical Builder and must be disclosed in reviewer provenance. Reassess path credit when hosts expose a verified author model and the coordinator can make a trusted not-weaker comparison. Until then, do not present the branch result as satisfying the stronger principle.
