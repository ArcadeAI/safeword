# Spec: Offload tests without blocking local work

## Intent

Safeword customers should be able to move expensive verification off their
development machine without adopting another test command or CI service. The
remote lane is opt-in and local testing remains the default. If preflight or an
explicit dispatch rejection proves that no remote run exists, the same
verification remains available locally instead of ending in a configuration
dead end.

## Intake Brief

- **Requested by:** Alex, after parallel Safeword sessions repeatedly queued focused tests behind long full-suite runs.
- **Cost of inaction:** Customers must keep expensive verification on their development machine, wait for it to finish before doing responsive work, or manually recreate Safeword's test intent in CI.
- **Reversibility:** Two-way door. The remote workflow is opt-in and removable; projects that do not enable it keep the existing local path.

## Vocabulary

- **Remote test lane:** An opt-in GitHub Actions job that runs Safeword-selected verification away from the customer's development machine.
- **Accepted dispatch:** GitHub Cloud's versioned dispatch API has returned HTTP 200 with a positive created workflow run ID. From this point the remote run is authoritative.
- **Indeterminate dispatch:** A dispatch request may have reached GitHub, but Safeword did not receive an explicit acceptance or rejection. Safeword must not automatically start a duplicate local run.
- **Local fallback:** Running the requested verification through the existing local test contract only when Safeword can establish that no remote run was created.

## Rave Moment

### offload-tests — The suite leaves, the work continues

- **Moment:** Safeword sends the same requested test-plan lane to GitHub, returns a live run link, and leaves the laptop responsive; if dispatch is unavailable, it plainly says why and resolves that lane against the current local checkout.
- **Beats:** Manually translating a local test command into CI YAML, hunting through an Actions page, or discovering after several minutes that an unavailable remote path ran nothing.
- **They'd say:** “I sent the suite to GitHub and kept working; when GitHub wasn't available, Safeword just ran the same check safely here.”

## Outcomes

- A customer can deliberately enable remote verification without it appearing or running in projects that have not opted in.
- The done-oriented test lane or full verification lane can run against an immutable pushed commit on GitHub-hosted infrastructure.
- The initiating user or agent can follow the remote run to a clear pass/fail result.
- When Safeword can prove remote dispatch did not occur, the same Safeword test-plan lane can resolve and run locally with a clear explanation of the actual local revision and dirty state.
- An accepted or indeterminate remote dispatch does not trigger a duplicate local run.
- Remote test failure, cancellation, and infrastructure failure remain visible and do not trigger a local rerun that could conceal or contradict them.
- Setup and upgrade do not replace customer-authored workflow changes.

## Decisions

- The public project control is `safeword project test-execution set local|remote-preferred`; `safeword project test-execution status` reports configured mode, effective mode, provider availability, and any recovery action without mutation. `local` is the default. `remote-preferred` deliberately communicates that a valid request may fall back locally only while Safeword can prove dispatch never occurred. The set command invokes the same reconciliation used by `setup` / `upgrade` and exits zero only when the requested mode is effective; interrupted or conflicted installation may therefore report configured `remote-preferred` but effective `local` with recovery guidance.
- A contributor may optionally set the default for the current worktree in `<namespace-root>/personal/config.json`, normally `.project/personal/config.json`: `{"schemaVersion":1,"testExecution":"local"}` or `{"schemaVersion":1,"testExecution":"remote-preferred"}`. The file is absent by default and is never created by setup. Setup idempotently adds anchored `/personal/` to the resolved namespace root's `.gitignore`, preserving authored rules; an already tracked file is never deleted or untracked, but status warns that it is not private. Default/legacy/custom namespace roots resolve through the existing namespace contract, and personal config is deliberately worktree-local rather than silently shared across worktrees.
- Execution preference precedence and status display order, highest first, are: one-run `--execution`; current worktree personal config; effective project mode; built-in `local`. `test-execution status` prints those four scopes in that exact order with exact source paths and configured values, prints command scope exactly as `not applicable` because status accepts no per-run override, and identifies the winner, installed provider identity and resulting effective behavior. An actual test request reports its supplied command override or `absent`. This follows mise's local-config ergonomics and Git's origin/scope transparency rather than hiding the winning value.
- Personal config changes only request preference. It cannot publish project opt-in, install or remove a workflow, redefine trusted workflow identity, make an uninstalled provider eligible, authorize dispatch/fallback, weaken validation, or mutate project state. Thus personal `local` may opt one contributor out of an installed remote default; personal `remote-preferred` in a project without the exact managed installation reports that preference but remains fallback-eligible locally. A command-line override wins for one request and changes neither personal nor project bytes.
- Personal config is a contained regular JSON file of at most 65,536 bytes opened without following symlinks below a pinned resolved namespace-root parent. Safeword rejects link count above one and revalidates leaf and parent object identity across classification, open, read and final verification. Its raw object has exactly `schemaVersion: 1` and `testExecution: "local" | "remote-preferred"`, with no duplicate or unknown keys. Absence means no override. Malformed, oversized, unreadable, wrong-version, non-regular, linked, replaced, escaping or otherwise invalid personal config fails with `SAFEWORD_TEST_EXECUTION_INVALID`, names the origin, executes nowhere and changes nothing; it never silently falls through to project remote execution.
- Personal-config parser and filesystem coverage is frozen independently in the planned literal test artifact `packages/cli/tests/fixtures/test-execution-personal-config-v1.json`. Stable fixture IDs cover each JSON token/schema/type/value, size, object-kind, link, containment, replacement and worktree-isolation case; tests require exact ID-set and cardinality equality and execute each fixture in isolation without importing production parser tables.
- Opt-in is recorded in two explicit Safeword project-configuration states reconciled by the set command and by `setup` / `upgrade`: durable `requested` intent is fsynced before managed-path mutation, while `installed_identity` activates remote eligibility only in the same journaled commit as the exact workflow and identity pair. A crash with requested intent but no installed identity is locally fallback-eligible, never remotely eligible. Projects in local mode receive no managed workflow or remote runs.
- Verification runs through `safeword project test --lane done|full [--execution local|remote-preferred]`. With no override, it uses the effective project mode. `--execution local` starts no dispatch; `--execution remote-preferred` attempts remote execution only if the managed installation is already effective and otherwise uses the same proven-no-dispatch local fallback. An override never changes project configuration or installs/removes managed files. Only the exact mode and lane enums are accepted; duplicate, unknown, extra-positional, or unsupported option syntax is invalid and executes nowhere with `SAFEWORD_TEST_EXECUTION_INVALID`.
- The first provider is GitHub Actions. Other CI providers are deferred behind the same execution-plane contract.
- V1 remote eligibility requires a clean local HEAD equal to the tip of a branch pushed to the same GitHub repository that receives the dispatch. Dirty, unpushed, detached, unauthenticated, unsupported-repository, not-yet-installed workflow, or a valid checkout tracking an upstream branch in a different canonical GitHub repository use local fallback. The public test command accepts no caller-supplied revision, ref, owner, or repository option; those identities are derived from authenticated Git and GitHub state only. Uploading an uncommitted patch is deferred as a separate security-sensitive capability.
- Request validation happens before remote eligibility. Invalid lane/execution syntax, any unsupported revision/ref/owner/repository option, a production Git HEAD acquisition that exits nonzero, times out, is signal-terminated, or returns empty/unborn output, or a successful read that is not exactly one 40-character lowercase hexadecimal SHA terminates with `SAFEWORD_TEST_EXECUTION_INVALID` and no execution, pending record, dispatch, or configuration mutation. Automatic fallback is allowed only for a valid request when eligibility checks or an explicit GitHub rejection establish that no remote run exists. A network-ambiguous dispatch is surfaced as indeterminate instead of risking duplicate execution.
- V1's public test command accepts lanes `done` and `full`. `done` selects `safeword project test-plan --kind test`; `full` selects `safeword project test-plan --kind verify`. A plan entry's command is explicitly trusted UTF-8 POSIX shell source, not an argv array. The executor passes the exact independently observable rendered-script bytes as the single script argument to its pinned shell executable and fixed option argv, uses the entry working directory as the child cwd, and supplies only the independently enumerated inherited-and-managed environment contract; Safeword does not normalize, split, or reconstruct command text. The managed remote runner resolves that kind after checking out the immutable target by invoking the exact pinned Safeword CLI inside the checkout; no locally resolved commands, availability results, or exits are transported. Local execution and fallback resolve inside the local checkout. Each plane consumes its resolver's real plan entries and preserves shell/script bytes, environment, working directory, availability, ordering, and exit status. Neither path maintains a second runner-selection table.
- Plan execution has one cross-plane abnormal-process contract. Spawn `ENOENT` exits 127 and `EACCES` exits 126 with `SAFEWORD_TEST_PLAN_START_FAILED`; SIGTERM is reported as signal termination and maps to 143; wrapper cancellation maps to 130 after contained descendants exit; output forwarding failure maps to 74 with `SAFEWORD_TEST_EXECUTION_IO`. The first abnormal entry stops later entries, is never automatically rerun, closes every pipe, and proves its execution container empty. Remote steps preserve those numeric exits as a failed or cancelled authoritative workflow conclusion; local execution returns them directly.
- Both v1 lanes are broad. In Safeword's own repository, local fallback therefore reaches the package-test scheduler through the unchanged resolved command as a broad run; BBNZ68 never translates either lane into explicit-file arguments or a focused permit.
- Dispatch sends `X-GitHub-Api-Version: 2026-03-10` and uses HTTP 200 whose raw top-level object contains exactly the pinned documented member set: integer `workflow_run_id`, string `run_url`, and string `html_url`. The run ID must be in the inclusive range 1..9,223,372,036,854,775,807 and is the sole correlation boundary; the two response URLs are schema-validated but never opened or trusted, because Safeword derives both URLs from frozen canonical identity and the exact ID. A literal independent manifest and mutation tests enforce exact set, cardinality, uniqueness, and type parity. Any unknown, omitted, duplicated, mistyped or malformed member makes acceptance indeterminate. Missing, zero, negative, fractional, string-encoded, out-of-range, duplicate, or malformed identifiers are likewise indeterminate; parsing preserves the exact int64 value without IEEE-754 rounding. Legal JSON framing is ignored. Safeword does not discover the run by timing or branch heuristics.
- Raw rejection authority is decided before client-library header normalization. Obsolete folding, control bytes, multiple physical header lines collapsed into one value, conflicting transfer framing, truncated bodies, and invalid UTF-8 remain indeterminate and can never authorize local fallback.
- Remote URL parsing accepts only exact credential-free `https://github.com/<owner>/<repository>[.git]` and exact `git@github.com:<owner>/<repository>[.git]` candidate grammars. Owner and repository must be raw unencoded path components, only one terminal `.git` suffix may be removed, and authenticated GitHub API metadata remains canonical. Embedded user information, credentials, query, fragment, ports, non-`github.com` hosts, ambiguous SSH/SCP forms, percent-encoded identity, malformed paths and repeated suffixes are rejected before authentication or API use. If no separately valid canonical candidate remains, the valid test request is remotely ineligible and follows proven-no-dispatch local fallback.
- Accepted terminal conclusions have stable numeric exits: success 0, failure 1, cancelled 130, action-required 2, neutral 3, skipped 4, stale 5, timed-out 124, startup-failure 125, and an unsupported non-null terminal value 70. The accepted remote result stays authoritative and never triggers an automatic local rerun.
- The dispatch endpoint is GitHub Cloud's `POST /repos/{owner}/{repo}/actions/workflows/{workflow_file}/dispatches` over HTTPS with `Accept: application/vnd.github+json` and `X-GitHub-Api-Version: 2026-03-10`. Safeword derives API and HTML run URLs from the authenticated `github.com` host, canonical owner/repository identity, and returned positive ID; it never opens a response-provided host or redirect. HTTP 204 or a 200 without a positive ID is indeterminate because a run may exist.
- Preflight observes and validates the repository's default-branch name and tip SHA. POST raw JSON parses to exactly two top-level keys: `{ "ref": <observed default branch name>, "inputs": { "request_id": <64 lowercase hex>, "target_ref": <canonical refs/heads ref>, "target_ref_digest": <64 lowercase hex SHA-256 of target_ref UTF-8 bytes>, "target_sha": <40 lowercase hex>, "lane": "done" | "full" } }`. `inputs` has exactly those five keys. Duplicate keys at either level are rejected from the raw token stream before ordinary JSON object construction; member order and insignificant legal JSON whitespace are not authoritative. Inputs are data and `ref` is never reconstructed from user text. The accepted run's workflow-source SHA must equal the observed default-branch SHA and its exact workflow bytes must match the trusted identity. A rename or movement that causes rejection may fall back only under the conclusive-response rules; an accepted run with different source is an authoritative integrity failure.
- Dispatch is attempted once and is never automatically retried. V1 disables proxy use and accepts rejection authority only over a direct connection to canonical `api.github.com` whose TLS chain and hostname pass the system trust store; projects requiring a proxy are remotely ineligible at preflight and use local fallback before POST. A conclusive rejection requires status 400, 401, 403, 404, or 422; exactly one case-insensitive `X-GitHub-Request-Id` header whose optional HTTP whitespace is trimmed and whose remaining value matches `[A-Za-z0-9:-]{1,256}`; a Content-Type whose trimmed media type is ASCII-case-insensitive `application/json` with no parameters; and a body no larger than 65,536 bytes parsing to an object with required nonempty string `message`, optional opaque string `documentation_url`, and optional canonical ASCII `status` matching `^(400|401|403|404|422)$` and equal to the HTTP status. `documentation_url` is never opened or used as authority. No other member is accepted. Duplicate raw keys or headers are never combined; arrays, nested objects, nulls, non-string values, parameters, or undocumented members are indeterminate. Transport errors, proxy/intermediary responses, timeouts, 5xx responses, and every other outcome are indeterminate.
- Dispatch disables automatic HTTP redirect following. Any 3xx response is indeterminate, and Safeword never forwards GitHub authorization to a redirected origin or treats a redirect target's response as conclusive GitHub evidence.
- Before POST, Safeword atomically writes a local transient pending record containing a random 256-bit request token and a machine-keyed MAC over the complete record; record-schema and Safeword CLI versions; authenticated actor; canonical repository identity; exact Actions workflow ID and path; observed default-branch name and source SHA; trusted exact-byte workflow hash and managed workflow version; target branch, its digest, and SHA; lane; and start time. The token, lowercase SHA-256 of the canonical UTF-8 target-ref bytes, full target SHA, and lane form the exact run name `safeword:<64-hex-token>:<64-hex-target-ref-digest>:<40-hex-target-sha>:<lane>`. Both canonical target ref and digest are workflow inputs, and the workflow recomputes the digest before repository code. The MAC and key never leave the machine. The pending record is gitignored, contains no GitHub credentials, and rejects a token already present in the repository's open records.
- Request-token generation reads exactly 32 bytes from the production OS cryptographic entropy source and encodes them as 64 lowercase hexadecimal characters. A duplicate open token is discarded and regenerated for at most eight total entropy attempts; success on attempt eight is allowed, while eight duplicates fail securely without a ninth attempt, record, or POST. Entropy failure or a short read fails closed.
- Resume first authenticates the complete local record MAC, then uses a recorded run ID. Without one, it lists that workflow's `workflow_dispatch` runs on the default branch, paginating within GitHub's filtered-result limit and polling for bounded visibility delay, then matches exact workflow ID; the exact run name containing random token, target-ref digest, full target SHA, and lane; authenticated actor; and workflow-source SHA. Local or GitHub wall-clock time is not an authority field: clock skew or discontinuity cannot exclude an otherwise exact match. Exactly one match becomes accepted; no match remains pending; duplicates—including a direct dispatch that replayed the visible run name—remain indeterminate and require the user to select a run ID that passes every frozen identity check. Recovery never authorizes fallback or redispatch.
- The frozen default-branch name records where dispatch and discovery were performed before acceptance; after a run ID is accepted, current repository default-branch metadata is mutable and is not compared as historical authority. Result authority instead uses the accepted run's immutable workflow ID/path/source SHA plus frozen target and correlation fields. A later default-branch rename or movement does not invalidate an otherwise exact accepted run.
- V1 requests 100 runs per page and reads at most 10 pages, matching GitHub's 1,000 filtered-result cap. New-run visibility polling lasts at most 60 seconds. Observation GETs permit at most five attempts and two minutes total; a `Retry-After` that exceeds the remaining budget stops retrying and preserves resume state. Tests inject the monotonic clock and backoff rather than sleeping.
- After HTTP 200, Safeword atomically adds the run ID to the record. Every monotonic transition—pre-dispatch pending, accepted run ID, observation progress, terminal result, and closure—is journaled with an owner-only per-request high-water anchor outside the replaceable pending-record file. The anchor retains the exact run ID, latest stage, terminal conclusion/exit, closure state, and record digest needed to reconstruct an isolated older pending-file rollback. Resume rejects a valid-MAC pending file behind an intact newer anchor and reconstructs anchored progress without POST, fallback, result regression, or request revival. This narrow guarantee protects only isolated pending-file restoration; coordinated rollback of the pending file, anchor and durability history is explicitly not detected or claimed without a hardware/OS monotonic counter. Watching and result retrieval use idempotent GET requests with bounded backoff for transient network, 5xx, and rate-limit responses. Authentication loss, retry exhaustion, or process interruption preserves the record and prints a concrete resume command; resume never redispatches. A terminal GitHub conclusion and anchor are persisted before the record is closed.
- Resume verifies against the identity frozen in the record, not the currently installed template. Upgrades preserve supported pending-record readers and their recorded hashes; an unknown newer schema or retired workflow identity fails closed with an explicit compatible-version recovery action and never reclassifies the run as trusted.
- The workflow definition is dispatched from the repository's default branch. A full commit SHA is eligible only after Git establishes it is local HEAD and exactly equals the chosen same-repository remote branch tip. The job checks out that SHA with persisted credentials disabled.
- Before POST, Safeword reads the workflow file at the observed default-branch SHA through GitHub's contents API and requires its exact managed content identity. After receiving the run ID, Safeword reads the run's immutable workflow-source SHA and verifies the file identity there too. Preflight divergence uses local fallback; post-dispatch divergence is an authoritative integrity failure with no automatic local rerun.
- GitHub's v1 `workflow_dispatch` contract selects a movable branch or tag ref; it does not bind dispatch to previously verified workflow bytes. A default-branch movement between preflight and GitHub resolving the dispatch can therefore start changed repository-controlled workflow code before Safeword observes the accepted run's immutable source. V1 does not claim to prevent execution by a repository maintainer who can already change that workflow. It limits the added exposure by sending no Safeword secret or local GitHub credential into the job, then rejects the run as an authoritative integrity failure as soon as source identity differs. Such a run never becomes Safeword evidence and never triggers automatic local fallback.
- Dispatch accepts only the `done` and `full` lane enum. Immediately before checkout, the workflow repeats lane validation and observes through the same repository's refs API that the supplied full SHA equals the supplied branch tip. That observation defines the invariant; later branch movement does not invalidate evidence for the immutable SHA. A direct/manual dispatch or a ref that moved before this observation terminates remotely without running repository code.
- In-job trusted pre-checks do not call Actions run or workflow metadata APIs. They validate raw dispatch inputs; recompute the target-ref digest; compare immutable `github.workflow_sha` and other built-in context supplied by GitHub; and use only the contents-authorized refs API to compare the target branch tip. Workflow ID/path/source, actor, and run-name correlation are checked by the local CLI against the accepted run after dispatch. Disposable private-repository evidence proves these pre-checks work with effective permissions exactly `contents: read`.
- The branch input is the current branch's canonical full `refs/heads/<name>` ref after `git check-ref-format --branch` validation; detached HEADs, tags, abbreviated refs, option-like values, and non-branch refs are ineligible. Both CLI and workflow compare its tip through the GitHub refs API using percent-encoded path data, never by shell evaluation or refspec construction.
- Safeword records the installed workflow's managed version and content identity. Setup/upgrade compares the current file with that installed base: an unchanged managed file may reconcile to the new version, while any customer divergence produces a no-mutation conflict with recovery guidance.
- Workflow identity is lowercase SHA-256 over the exact decoded file bytes with no newline or YAML normalization. The trusted expected hash is derived from the workflow template bundled in the installed Safeword CLI version and registered in schema; project configuration records installation history but cannot redefine the trusted bytes.
- The managed workflow enumerates every `uses` position and pins every action to a full commit SHA. V1 forbids reusable-workflow references, including local ones, so transitive workflow dependencies cannot escape the exact-byte contract. It invokes an exact Safeword CLI version and does not download or execute an unpinned helper before trusted revision, lane, and workflow-source checks complete. Repository-owned test commands and their declared dependencies remain the code intentionally under test, not part of the workflow-identity claim.
- “No Safeword-provided secret” means the authoritative ten-category Safeword-owned channel inventory introduces no Safeword or local API secret value/reference: project-configuration serialization; pending-record serialization; HTTP request headers; dispatch JSON body; `workflow_dispatch` input declarations; workflow-, job-, and step-level environment mappings; declared and effective action inputs; `run` command source and resulting arguments; files created by the managed workflow; and Git or HTTP credential-helper configuration. GitHub's automatically provided job token is an explicit non-Safeword exception required for private-repository refs access and checkout: effective permission is exactly `contents: read`; it may appear only as authorization to canonical GitHub endpoints and as the checkout action's effective token input; checkout sets `persist-credentials: false`; and the token is absent from declared environment/run mappings, repository-process environment and arguments, created files, and post-checkout Git credential configuration. The local GitHub API credential remains allowed only in the direct canonical `api.github.com` Authorization header before dispatch; it is never redirected, persisted, placed in another header, or exposed to the job. The inventory distinguishes workflow-declared mappings from effective runtime action inputs, records each category as present or explicitly absent, and contract tests inspect both with representative sentinels. This does not claim the customer repository has no independently configured Actions secrets. Exact managed bytes, effective-runtime capture, and dispatch/config serialization are the authority for this property.
- Installation and upgrade stage the new workflow, identity, and installed-identity configuration, then write a transaction journal naming all exact old and new bytes before replacing any live member. Disable stages no tombstone files; its durable journal names the exact old bytes and an absent new state for each member before unlinking. On restart, matching old/new states across all three members are completed or rolled back deterministically; any member matching neither side stops at a no-mutation conflict. The journal is removed only after workflow, identity, and installed-identity configuration match the committed side.
- Deterministic reconciliation policy is: if all three live members still match the old set, retain the old set and remove unused staged new files; if one or two members match the new side and the rest match the old side, complete the exact new set; if all match the new set, finalize it; any other combination preserves live bytes and stops at conflict. The journal is removed last.
- The same state machine represents initial installation with an absent old set and disabling with an absent new set. A pre-existing unowned path never counts as absent or managed and produces a no-mutation conflict. Disabling removes an unchanged managed workflow, identity, and opt-in configuration transactionally only when no authenticated pending request depends on them; customer-modified bytes are preserved as conflict. Restart classifies the actually observed durable artifacts rather than predicting whether a rename that lacked directory fsync survived a crash.
- Reconciliation correctness has two evidence layers: deterministic state-machine tests inject every observable combination of workflow, identity, journal, and staged bytes; supported-platform subprocess crash tests interrupt every staged-member write/fsync, journal write/fsync/rename/directory-fsync, live-member rename/directory-fsync, exact-set verification, journal unlink, and final directory-fsync boundary. Restart records whichever bytes actually survived and requires that observed combination to enter the matching deterministic row. The platform test never assumes an un-fsynced write, rename, or unlink must survive or disappear.
- The pinned workflow validator opens the exact absolute `GITHUB_EVENT_PATH` file without following a substituted link, records its pre-parse SHA-256, and parses those raw bytes before checkout. A byte-preserving test fixture proves duplicate-key rejection. When GitHub itself serializes a normalized canonical event, Safeword validates only the exact bytes it actually receives plus the managed workflow's closed input declaration; it does not claim to recover or observe duplicates discarded before file creation.
- Local fallback does not acquire an outer checkout lock; the unchanged resolved command and its real wrapper remain the sole owner of any checkout mutex. Immediately before plan resolution/invocation and after the command returns, fallback computes a SHA-256 over length-prefixed Git-visible records: HEAD, porcelain-v2 `-z` status, binary cached and worktree diffs, submodule state, and untracked entries from `git ls-files --others --exclude-standard -z`. These boundaries deliberately include any scheduler wait inside the invoked command; they do not claim to observe the wrapper's later process-start instant. Regular files are streamed into the digest; symlinks contribute link text and are never followed; directories are represented by their contained listed paths. Special, unreadable, or concurrently changing entries make the fingerprint indeterminate rather than being opened.
- Fingerprinting enforces versioned ceilings of 100,000 Git-visible files, 1,073,741,824 hash-input bytes, 30 monotonic seconds, and three total attempts including at most two retries. Byte accounting includes every record's type/domain tag, length prefixes, path bytes, payload bytes, raw Git command output, regular-file bytes, and symlink link text exactly as supplied to the hash; oversized Git output can exceed the ceiling before file streaming. Exceeding one makes evidence indeterminate with the literal limit message. It repeats each read until two consecutive fingerprints agree or the attempt limit fails. A changed or unstable endpoint fingerprint makes the result indeterminate and reports both states; it is never presented as evidence for the earlier checkout.
- Matching endpoints establish boundary consistency, not proof against an external ABA mutation changed and restored during execution. Ignored files, external toolchains, environment variables, transient non-participating writers, and plan dependencies outside the repository are named evidence limitations rather than silently included in the source fingerprint.
- User-facing fallback evidence says only that invocation-boundary fingerprints matched; it never says or implies the checkout remained stable throughout execution.
- V1 applies one evidence policy to both local lanes, with fingerprint integrity taking precedence over command exit. Changed, unstable, or unreadable fingerprints make the overall evidence indeterminate; Safeword reports the raw exit separately but does not attribute pass or failure to the identified checkout state. With matching fingerprints, a non-zero result is a local failure for that execution, while zero is `passed with evidence limits`, listing ignored files, external toolchains, environment variables, non-participating writers, and out-of-repository dependencies as unmeasured; it is not presented as remote-equivalent or environment-complete proof. V1 does not silently promote any limitation by lane.
- The pending-record MAC key is 256 random bits stored outside the repository in Safeword's per-user machine configuration directory with owner-only permissions and a stable key ID. Rotation is refused while any pending record references the active key; retired keys remain available until their authenticated records close.
- A missing, unreadable, replaced, or mismatched key makes every pending-record field unauthenticated and fails closed. Safeword does not redispatch, fall back locally, accept user-edited identity fields, reclassify the run, or derive output or links from those bytes. Unauthenticated recovery emits only a fixed ASCII error code and bundled record-independent guidance; it contains no record-derived URL, identifier, control character, bidi character, terminal escape or hyperlink and opens nothing. Only after a valid MAC may recovery validate canonical field grammar and render canonical non-secret identifiers as inert escaped text for manual inspection; that inspection cannot become authoritative Safeword evidence without the valid recorded key.
- The exact managed workflow pins its verification request to an immutable commit, allowlists supported lanes, grants only `contents: read`, and does not inject dispatch input into shell source. These permissions describe the trusted managed bytes, not arbitrary repository-controlled bytes substituted during the documented dispatch-ref race.
- Selected-file execution, secret-bearing test environments, fork-origin dispatch, GitHub Enterprise Server, cancellation propagation, remote retry, and other CI providers are deferred from v1. A later explicit `--execution local` request after an authoritative remote conclusion is a separately identified run and cannot replace or reclassify the remote evidence.
