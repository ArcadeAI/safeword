# Impl Plan: Route local retros through the durable server

**Status:** planned
**Implementation state:** Code paths are built, but production cutover evidence is incomplete.
**Planned on:** 2026-08-29

## Approach

The riskiest assumption is that collector acceptance can transfer recovery without coupling anonymous intake to GitHub authority. The first deliverable is one real-process acceptance-to-reclaim integration: submit immutable `v3` bytes, restart after a lease is claimed, reclaim the same row, hand it to the real relay with only GitHub HTTP controlled, and observe one filed disposition for the original request identity.

Build six tightly coupled slices; they remain one feature because none is independently safe to cut over:

1. **Immutable local request and bounded dispatch.** Extend the current public-retro attempt record into an atomic `v3` record containing UUIDv4 request ID, session scope, exact serialized bytes, and a route stamped at capture (`direct-v2` or `server-v3`) before transport. Re-extraction reuses the saved offset identity; later offsets differ; conflicts preserve both records. Drive each installed Claude, Codex, and Cursor dispatch payload through the real SafeWord CLI entry point with only collector HTTP, direct-GitHub HTTP, and clock controlled. One session-stop drain owns one 750 ms deadline, and each attempt receives only the remaining budget; assert the second attempt receives at most 350 ms after a 400 ms first attempt. Assert every outcome is absent from the session-stop result, missing project identity makes no request, and the server-dispatch path preserves the expected spool state while issuing zero direct-GitHub requests for acceptance, legacy quarantine, typed rejection, timeout, and unreachable outcomes; only durable `v3` acceptance releases local recovery. Retro Filer separately owns direct filing of a route-stamped pre-cutover `direct-v2` draft. Extend the schema-managed `packages/cli/templates/guides/retro.md` disclosure and verify its existing schema entry through install/reconcile. Primary proof: CLI integration tests; supporting table tests cover UUIDv4, 4 KiB finding, 50-finding, 256 KiB envelope, sanitization, and Cursor local/managed/unknown classification. Covers NTB1.R1-R3, TBU1.R1-R2, TBU1.R4, SWM1.R2.
2. **Collector-owned `v3` queue.** Add a forward-only SQLite migration that keeps v1/v2 rows inert and stores `v3` state, exact bytes, a server-derived collector-envelope digest, receipt, one server acceptance timestamp, lease owner/deadline, attempts, and terminal metadata atomically. The `v3` duplicate key is the transport-independent request UUID alone; the harness-inclusive v1/v2 compatibility tuple never applies. The collector-envelope digest covers the exact admitted `v3` bytes and is never validated as the relay filing-payload digest. Add private authenticated claim, quota-reserve, renew/release/complete, payload-free lifecycle, and separately authenticated and audited worker-read and break-glass routes; public intake can write but cannot inspect or file. Primary proof: real HTTP server plus real SQLite integration tests, including restart, same UUID replayed across different harness metadata, duplicate/conflicting bytes, envelope-digest stability, expired lease reclaim, payload-free routine listing including unauthenticated denial, ordinary-operator payload denial, audited worker/break-glass principals, and absence of relay credentials/GitHub traffic. Covers TBU1.R2, TBU1.R6.
3. **Private worker to existing relay.** Add a small worker entry point that leases FIFO `v3` rows from the collector over Railway private networking and submits the original bytes plus collector-envelope digest to the relay as a new least-privilege `collector-worker` principal. The relay validates that envelope digest before mapping findings, then derives its existing filing-payload digest from the mapped filing request; the two digests never substitute for each other. The collector retains its own acceptance timestamp for queue observability, while the relay records a fresh acceptance timestamp and retry deadline when filing ownership transfers and persists that deadline unchanged across retries. Relay acceptance is filing ownership; before it, lease expiry returns ownership to the collector. Primary implementation proof: packaged collector + worker + real relay store with only GitHub HTTP controlled; inject a long pre-lease queue delay, crash-after-claim, 5xx/timeout retry, retry exhaustion, lost create responses, incomplete scans, sanitized reads, similarity, lone markers, and marker-looking finding content. Assert the delayed record still files, the fresh relay deadline remains stable, no second create occurs, deadline exhaustion alerts, and only a complete raw scan of relay-owned exact markers suppresses creation. Slice 5 separately owns the real production fault artifacts required by SWM1.R3. Covers TBU1.R3, TBU1.R5, SWM1.R3.
4. **Limits and relay compatibility.** Raise client and collector bounds together to 256 KiB; enforce 4 KiB serialized findings and 50 findings without splitting or replacement identities. Persist rolling intake and filing quota windows in collector SQLite so restarts cannot reset the 60/minute intake, 20/hour global filing, or 5/project/hour filing bounds. The collector's authenticated quota-reserve operation atomically selects FIFO eligible work and records filing capacity; worker completion releases or finalizes that reservation without reading SQLite cross-host. Collector maintenance reads stored acceptance/quota timestamps, moves work blocked for 24 hours to dead letter, and persists a payload-free alert. Primary proof: restart-aware real-store integration tests with injected clock; collector intake tables assert typed rejection and zero `v3` rows for oversized envelopes, non-v4 identity, user identity, transcript/prompt text, tool/file content, secret material, and marker authority syntax; a maximum-batch relay wiring test preserves all findings. Covers TBU1.R4 and SWM1.R4.
5. **Cutover and evidence.** Prerequisite: the existing relay readiness manifest must first enable production filing from its drain-throughput, artifact-hash, ancestry, and running-build evidence. Then extend the separate local-cutover readiness manifest with independently authoritative per-harness collector and relay observations, fault outcomes, build ancestry, and running-build attestation. Committed identifiers and hashes alone cannot enable this gate. Until a verifier can establish that production provenance, local cutover remains unconditionally fail-closed. A per-source maintainer canary disables direct filing only for its own captured source; the global default changes only when Claude Code, Codex, and Cursor local canaries and required production fault artifacts pass. Every draft follows the immutable route stamped when it was captured, never a later clock/flag inference. Primary proof: evaluator tests currently prove the unavailable-authority state cannot enable; future enabling tests must use authoritative collector/relay evidence and reject managed-cloud Cursor, unknown provenance, mismatched identities, missing fault outcomes, and non-authoritative recovery claims. A real Retro Filer drain integration covers a `direct-v2` draft after cutover and a new `server-v3` capture. If relay readiness or authoritative production evidence remains unavailable, this ticket remains in progress at the production-evidence gate and does not claim completion or move that work to a weaker follow-up. Covers TBU1.R7, SWM1.R1, SWM1.R3, SWM1.R5.
6. **Deployment and disclosure.** Deploy the worker as a private Railway service, keep collector and relay single-replica, configure the `collector-worker` principal and quotas, and extend CI deployment/canary wiring. Update README and website disclosure for included/excluded fields, zero-setup local routing, opt-out, recovery semantics, and operator inspection. Primary proof: Docker/package tests, workflow contract tests, production health/readiness receipts, and the three real harness canaries.

Wiring boundaries are explicit: tests use real filesystem persistence, SQLite, HTTP servers, request parsers, worker loop, relay state machine, and installed-harness payloads; only external GitHub/network timing, clocks, and production platform state are controlled. Raw REST issue bodies are the only duplicate-decision source. Sanitized MCP reads, similarity, incomplete scans, lone markers, and marker-looking user content cannot authorize suppression; authority markers are parsed only from the relay-owned body region.

Splitting checkpoint: no split. Although six components move, the acceptance-to-filing ownership chain and cutover gate form one load-bearing vertical slice; separate tickets would either duplicate the contract or leave an unsafe partially enabled route.

### Recorded Decisions

| Decision | Choice | Alternatives considered | Rejected because |
| --- | --- | --- | --- |
| Durable server ownership and work handoff | Collector SQLite atomically accepts `v3`; a private worker leases rows and hands exact bytes to the relay | Move public intake into relay; synchronous collector-to-relay call; add PostgreSQL/queue | Relay intake would colocate anonymous traffic with filing authority; synchronous handoff loses accepted work on failure; PostgreSQL is unnecessary at current single-replica volume |
| Client identity and recovery | Upgrade the existing per-project attempt record to one immutable atomic `v3` request per saved transcript window | Random ID per send; reuse the external relay outbox; new parallel outbox | Per-send IDs break dedupe; external outbox violates zero setup; a parallel store duplicates recovery state |
| Authentication and authorization | Public write-only intake plus authenticated private claim/read routes and a least-privilege `collector-worker` relay principal | Put a filing credential in clients; reuse an existing harness principal; trust Railway network alone | Client secrets are extractable; harness principals misattribute authority; network location is not authorization |
| Retry and duplicate authority | Collector lease expiry before relay acceptance; existing relay retry/ambiguity lifecycle after acceptance; complete raw REST scans of relay-owned markers only | At-most-once dispatch; blind create retry; similarity or sanitized MCP reads | At-most-once loses work; blind retry duplicates issues; non-authoritative evidence can suppress real findings |
| Rollout | Per-source canaries and a build-bound global readiness manifest; pre-cutover drafts finish their original route | Immediate global flag; dual filing; customer opt-in | Immediate cutover is unproven; dual filing duplicates; customer action violates zero setup |
| Launch limits | Configurable SQLite-persisted quota windows and FIFO scheduling in the supported single-replica topology | In-process counters; distributed rate limiter; unbounded drain | Memory counters reset on restart; distributed infrastructure is premature; unbounded anonymous intake can create unbounded GitHub work |

Figure It Out debate: moving intake into the relay is operationally compact but crosses the strongest trust boundary; synchronous forwarding is the smallest code change but cannot make collector acceptance durable. Extending collector SQLite adds one lease state machine yet preserves the existing public/private split and has no new dependency. Recommend the collector queue because acceptance and ownership transfer become one transaction. **Premortem:** this fails if the collector is scaled to multiple hosts against one volume; keep one replica and migrate the store boundary to PostgreSQL before scaling. **Next:** implement the immutable client `v3` request and collector acceptance/restart wiring test first.

## Known deviations

The relay's current client-supplied retry-deadline contract changes for collector-owned `v3`: collector acceptance remains collector-only queue metadata, while the relay records its own acceptance time and owns a fresh 24-hour deadline from first relay acceptance. This is required so durable collector queue time cannot consume the filing retry window; the architecture decision and migration tests record the change. Existing direct relay clients retain their current contract.

## Assessment triggers

- The existing relay readiness manifest remains disabled: production terminal-filing canaries and global local cutover stay blocked, while implementation and non-production verification may continue.
- More than one collector or worker replica, or any need to mount SQLite across hosts: migrate the store/rate-limit boundary to PostgreSQL before scaling.
- Sustained intake or queue depth makes one SQLite writer, FIFO scans, or the configured filing quotas miss operational objectives.
- A new harness or cloud carrier becomes supported: add truthful runtime classification and a real build-attested canary before it can satisfy readiness; Cursor Cloud remains deferred to #3476.
- A harness invocation mode does not emit its lifecycle hook: exclude that mode from canary evidence rather than substituting process presence; Claude print mode currently emits no Stop hook.
- GitHub adds a trustworthy create idempotency key or changes raw issue-body visibility: reassess marker-based ambiguity recovery.
- Marker collisions or hostile marker content appear in production evidence: tighten the relay-owned marker encoding/parser without broadening similarity authority.
- Reusing client credential helpers makes #1495 a readiness gate; otherwise it remains unrelated.
