# Impl Plan: Keep tasks and patches proportional

**Status:** planned
**Planned on:** 2026-11-19
**Revised:** 2026-11-19 after the scenario approval was refreshed.

## Approach

Installed workflow entry points send the accepted work description and discovered decisions to one CLI classification policy. The policy returns a route and reasons. Existing ticket creation and lifecycle adapters apply the route, and shared edit admission checks observable prerequisites against the active ticket. The inline ticket owns small-work proof and contributor handoff. Promotion keeps that ticket identity and hands the consequential decision to the existing feature phase gate. [Accepted Rules](spec.md) · [Scenarios](../../../features/keep-tasks-and-patches-proportional.feature)

Behavior-changing tasks require current evidence from a real failing test before production edits. Activate by default only on matched supported builds under YCFFNC after installed local and cloud proof, including actual RED acquisition. Old builds can miss the gate.

### Proof strategy

The riskiest assumption is that a live edit boundary can distinguish a structurally valid task from a task whose latest discoveries require feature planning. In the first R13 proof, put an unresolved public-contract choice in the accepted request or linked contract and omit it from the initial task declaration and facts. Run the installed workflow from that real source and attempt the production edit. Structural validation must pass while interpretation surfaces the omitted choice, routes to feature and blocks production. A control with the choice resolved privately stays task. Corrupt classification input must also stop.

### Persona consequences

- **Technical Builder:** Can select relevant proof and make reversible private choices locally. A consequential choice pauses the edit and preserves learned facts with their original boundary. Gate evidence proves the admitted operation, with semantic judgment still dependent on the supplied facts.
- **Non-Technical Builder:** Gets the next decision and retained progress through K3EBHB's presentation. Usability requires the distinct walkthrough there.
- **Contributor role (TBU or SWM):** Hands off a proportional record with named current proof and explicit human dependencies. The demo establishes contributor readiness for the exercised cases.
- **Safeword Maintainer:** Can inspect historical evidence, including failures, and hand off to the authorized actor. The user owns scope expansion, the designated approver owns any required approach decision, and authorized release and repository owners govern rollout and merge. Maintainer role and checklist completion confer no such authority.

## Decisions

### Recorded Decisions

- **Decision:** Semantic routing at the existing ticket and edit boundaries.
  **Choice:** The workflow interprets the request and supplies local fact schema v1 with accepted scope and outcome references, behavior and proof needs, consequential decision facts, optional declared type and active ticket identity, and affected surfaces and observed footprint for reevaluation. Require explicit known or unresolved facts. The CLI applies feature precedence for multiple flows, new persistent state or unresolved consequential behavior, shared contract, durable architecture, data ownership, migration or required proof boundary. Patch requires a fully established outcome, no new behavior contract, no feature trigger and sufficient existing or targeted verification without new regression proof. Residual work is task, split into bounded dependent tasks where needed. A declared or legacy type expresses intent. Typed CLI v1 returns the route and reasons with exit 0, requests missing facts or an incompatible capability with `action_required` and exit 2, and reports malformed input or policy failure as `failed` and exit 1. Both non-success results stop capable admission.

  Reevaluate at entry, on a discovered consequential trigger, or on crossing the project config thresholds. Projects without threshold keys use more than two files or more than one declared surface. A malformed configured value returns the typed failed result with exit 1. Capture the ticket worktree’s base revision at entry and retain it across commits and restarts. Observe paths changed from that base in the ticket worktree, including uncommitted and untracked paths and the proposed path when known. Exclude unrelated changes only when their ownership is established in the ticket evidence. Count surfaces as the union of the workflow’s declared affected surfaces and those identified by the current project surface catalogue and the affected caller or installed-entry evidence for the changed paths. Require explicit surface resolution when available evidence cannot distinguish the affected entries. In the installed R6 proof, commit the initial edits below the threshold, restart, and cross the threshold with the next proposed edit. Compare against the last recorded evaluation so unchanged above-threshold work does not fire repeatedly. Below-threshold checks stay silent when decisions are settled. Record a fresh evaluation before further production work on crossing.

  Feature triggers include introducing any new user flow or explicitly changing a shared public contract, even for a settled one-line change. Unresolved data lifecycle and compatibility decisions independently trigger feature, including retention without ownership change and backward compatibility without migration. Apply the same triggers at entry and reevaluation. The fact input distinguishes these consequences from settled private changes to established behavior.

  At entry and reevaluation the installed workflow reads the accepted request, ticket scope and exclusions, inherited Rules where applicable, and the referenced current public contracts, affected callers and recorded discoveries. Interpret those sources for each consequential trigger before sending v1 facts, with references to the evidence supporting the interpretation. The declared type and previous fact snapshot are inputs to check, not authority over that source material. Missing source or contradictory facts with no supported resolution stop admission and identify what to clarify. Bind decision currency to those source identities as well as the submitted facts. The policy only checks observable prerequisites and the supplied interpretation. The omitted-trigger live proof tests the host's semantic judgment separately.

  Bind each evaluation to the ticket ID, digest of decision-bearing ticket and scope facts, effective policy and thresholds, and the evaluated footprint and threshold band. Publish conditionally against the evaluated ticket version. At admission reread those facts and the observable footprint including the pending edit where known. A changed fact digest, policy, threshold crossing or conflicting update invalidates the prior admission. Pause and reevaluate from current state. Mechanical growth in the same band with settled decisions can continue. The gate covers the observed admission snapshot. External concurrent changes beyond that boundary carry no atomic edit guarantee.
  **Alternative considered:** Infer type from changed files or let host sizing prompts make the final decision.
  **Rejected because:** A tiny shared contract change and a large mechanical rename would route incorrectly, and host rules would drift.
  **Evidence reference:** [1] [Ticket creation](../../../packages/cli/src/commands/ticket-new.ts), [shared quality hook](../../../packages/cli/templates/hooks/pre-tool-quality.ts), and [native integration contract](../../../ARCHITECTURE.md#registry-driven-agent-integrations-with-native-trust-boundaries). The creation command demonstrates explicit type handling. The hook provides an existing production boundary. Neither establishes semantic classification.
  **Retrieval date:** 2026-11-19.
  **Applicable version:** Repository Safeword 1.2.0. Reuse repository contracts under the CLI package’s declared MIT license. Classification requires project facts only, with no external service or dependency added.

- **Decision:** Admit production from inline proof and promote in place.
  **Choice:** The inline task record names the agreed behavior, real actor entry point, test command, expected outcome and observed failing assertion. Tests and investigation can proceed before production admission. Reuse the existing executable-RED run validation and bind its trusted observation to the task contract, failing revision and declared proof inputs. Capture the existing entry point against the pre-test baseline and identify the target test and assertion before running it. The working agent checks the test diff, baseline entry point and runner output together, then records whether the named test actually reached that boundary and failed at that assertion for the agreed behavior. Bind that finding to the same runner observation and proof inputs. Admission requires a positive finding, the referenced baseline and test inputs, and a current run that exited with a failure and produced the expected assertion. A timeout, signal, skipped test or unresolved finding blocks admission. The runner establishes observed output and termination. The working agent establishes relevance from the linked sources. Missing, stale, setup, unrelated and invented-boundary failures keep production paused. Rerun the same test after the edit and record the pass.

  For a behavior-preserving task, require a current passing pre-edit run of an existing test or a new characterization test before admitting production edits. The working agent checks that the assertion exercises the protected behavior through the existing boundary and would fail on a concrete regression, then records the boundary, assertion, regression example and why the test would catch it. Bind that finding and run to the task contract and proof inputs. If an existing test lacks that protection, require passing characterization that supplies it. The installed R9 negative case deliberately regresses the behavior in a disposable fixture to demonstrate the old test stays green. Regular admission checks the linked finding and run and relies on the working agent for semantic adequacy. For a non-behavioral patch, require a recorded targeted check and the regression it can catch before the edit. Bind that selection to the patch scope and require the observed result at contributor readiness. Preserve GREEN and regression proof through private refactor. When a consequential in-scope decision appears, block production, preserve original investigation and exact proof references, and update the same ticket to feature and the owning phase. Behavior goes to define-behavior. Design and required proof boundary go to plan-implementation. Design entry requires confirmed applicable behavior and real provenance. Existing prerequisites still govern entry. Feature sequencing repair goes to plan-execution with an accepted current approach. A task sequencing adjustment stays inline. Drop out-of-scope ideas whose exclusion leaves the accepted outcome intact. Before applying feature precedence, classify a consequential out-of-scope discovery as a pending user scope decision in the v1 facts. Conditionally record it on the same ticket with its discovery reference and accepted-scope identity. Keep the task route, deny production admission, and return action_required with exit 2, including in headless runs. Resume only after recording the user’s decision against that discovery. On approval reevaluate the amended scope. On decline reevaluate the original scope and keep any incompatible work blocked. If the accepted scope or discovery changes while pending, refresh the record and require a current user decision.
  Before task TDD entry, validate the inline behavior, proof method and named actor boundary. Missing facts report the task incomplete. Investigation and clarification remain available before RED begins. Obtain the failing run in the normal project sandbox. Exercise actual run acquisition and write admission through installed CLI and the supported local and fresh cloud lifecycle paths. Include a solo run, a different test that prints the same failure text and a test that fails at a newly invented entry point. Use real runner output for these cases.

  For design-only promotion, enter Implementation Planning immediately if the applicable feature behavior already has current approval through the existing gate. Otherwise publish feature type, behavior definition, pending Implementation Planning destination, reason, original task notes and evidence links together. Use the notes to prepare the behavior still missing or unapproved, and ask the user only for an unsettled behavior or scope decision. A headless invocation records that decision on the same ticket and returns promptly. The ticket remains short of Implementation Planning until the existing scenario gate verifies approval. On restart, use the saved destination and keep the same ticket and evidence. After the approval passes, enter Implementation Planning and clear the pending destination in the same conditional write. Inline notes and a copied receipt do not establish approval.
  **Alternative considered:** Create a replacement feature ticket and copy passing proof, use the task's checkboxes as admission, or add a task RED review with the best available reviewer, including the same-agent fallback described in Independent Review Never Blocks.
  **Rejected because:** Replacement breaks retry identity and trails. A checkbox can mask absent RED or a changed proposition. A separate review with fallback would let solo work proceed, but adds a dispatch and a second proof path for the same inline evidence. A solo relevance finding is agent judgment and may be wrong. A valid runner observation alone cannot establish what behavior the test exercises.
  **Evidence reference:** [2] [Ticket writer](../../../packages/cli/src/utils/ticket-writer.ts), [phase provenance](../../../packages/cli/templates/hooks/lib/phase-provenance.ts), and [continuous quality gates](../../../ARCHITECTURE.md#continuous-quality-gates-loc--phase--tdd). The linked boundaries establish where to enforce and retain history.
  **Retrieval date:** 2026-11-19.
  **Applicable version:** Repository Safeword 1.2.0. Local ticket and proof references only. Existing review and human approval authority stays with their owning paths.

- **Decision:** Use an inline contributor checklist.
  **Choice:** Reuse checklist obligation and proof semantics. Materialize and display applicable inline rows at task or patch entry before contributor implementation. Resolve them independently of the feature execution-plan loader. Each row has linked current proof, a concrete inapplicability reason, or a named pending human actor and decision. Missing proof, a stale reference or a blank skip leaves contributor work open. With contributor work resolved, return ready for human review even when a named human dependency remains. Reject any claim of merge authority in the readiness outcome. Headless dispatch emits the record and returns.
  **Alternative considered:** Create a stub Execution Plan or make rollout approval a prerequisite for contributor readiness.
  **Rejected because:** Both impose feature or release ceremony before small work can reach a human.
  **Evidence reference:** [3] [Delivery checklist policy](../../../packages/cli/src/execution-plan/delivery-checklist.ts), [command boundary](../../../packages/cli/src/commands/delivery-checklist.ts), and [deterministic readiness evidence](../../../ARCHITECTURE.md#deterministic-readiness-evidence-status).
  **Retrieval date:** 2026-11-19.
  **Applicable version:** Repository Safeword 1.2.0. Same repository reuse and access boundaries. No external checklist dependency.

### Data applicability

Data applicability: Extend the existing ticket's inline record for decisions, proof and handoff, and use the existing feature artifacts when promoted.

| Subject | Decision and consequence |
| --- | --- |
| Purpose | Preserve why the route changed and what proof survives so interrupted work can resume. |
| Store and model | Existing ticket frontmatter carries route and phase. Existing inline record links the scope, decision, proof and checklist. Existing feature artifacts carry accepted behavior and design after promotion. |
| Schema and relationships | Keep the existing ticket ID and phase vocabulary. Associate linked proof with original behavior, boundary, revision and outcome. Maintain a single current route with historical evaluations in the work record. |
| Source of truth | Accepted ticket/parent and user dispositions own scope. Ticket owns current route. Test observation owns the reported result. Existing review receipts retain their exact authority. |
| Ownership and access | Existing authorized workflow writer records transitions. User owns scope/approval. No new actor gains write or approval rights. |
| Identity and integrity | Use ticket ID and expected ticket bytes for conditional writes under the existing writer boundary. Check identity and prerequisite provenance on resume. |
| Cross-system flow | Host adapters send decision facts to the CLI and receive route or blocked outcome. Headless handoff carries repo-relative evidence and pending role, with sensitive output kept in its original access boundary. |
| Lifecycle and retention | Stop production before promotion. Prepare compatible prerequisites without marking them approved. Publish type, phase, preserved references and reason together in the ticket replacement. Partial preparation or conflicting edits leave admission blocked. Retry the same decision against the current ticket, retaining existing evidence and avoiding duplicate promotion. |
| Migration and backfill | Keep completed records and historical receipts in place. In-flight work may resume its recorded, already-admitted scope under legacy rules. Apply the new contract on fresh routing or consequential reevaluation, retaining earlier proof for its original scope. No bulk rewrite. |
| Compliance | No new personal data collection or export. Persist project evidence and responsible role using existing access and retention. |
| Rollback | Reconcile installed assets as a matched bundle. Keep promoted features and their evidence. For an incomplete handoff, pause production and restore the capable runtime before retrying. A downgrade confers no gate or proof authority. |

### Rollout

Default on for new work on matched supported builds after coordinated activation. YCFFNC owns activation sequencing and the in-flight migration across hosts. Prove the matched bundle in dogfood and the named installed local and clean cloud boundaries before broad exposure. A capable adapter that detects an incompatible or missing classifier stops new admission and directs reconciliation. An old adapter or CLI can omit the new checks. Mixed builds carry no project-wide enforcement claim. Pause expansion on silent bypass in a capable build, unexplained false blocks or lost evidence, then reconcile to a matched known-good bundle while retaining ticket history and promotion state.

## Known deviations

Under **1. Structure enforces; instructions suggest**, task RED departs from independent or best-available review for judgments about one’s own work. The working agent checks the evidence directly to keep small-task admission within the existing inline workflow. The gate verifies the run and evidence binding. A mistaken relevance finding can still pass that gate. Reassess this choice if live installed cases show repeated false admissions.

The current handbook uses file-count sizing defaults. Replace their routing effect with the accepted semantic precedence for the affected surfaces during delivery. Preserve file and surface counts as reevaluation signals.

## Doc impact

README and the website workflow and ticket guidance need the three routes, inline proof and checklist expectations, threshold role, promotion behavior, and human handoff limits. ## Assessment triggers

Reopen this design if an installed host bypasses the shared classifier, proposed edits can cross a configured signal undetected, the writer cannot preserve evidence under concurrent updates, RED relevance cannot be judged from retained observation, the per-edit check exceeds the existing hook latency budget, or proportional checklist reuse needs a new authority or storage boundary.
